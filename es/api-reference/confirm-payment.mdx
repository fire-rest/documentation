---
title: "Confirmar pago"
api: "POST https://app.fire.rest/api/v1/adapters/xmart/stores/orders/{orderId}/confirm-payment"
description: "Registra el cobro de una orden abierta y la salda. Acepta varios medios de pago en un mismo cobro y también los intentos rechazados."
authMethod: "bearer"
---

Cierra el ciclo del **pago diferido**: la orden nació abierta, la cocina ya trabajó, y acá llega el
cobro. Si hay al menos un medio aprobado la orden pasa a `COMPLETED` y arranca la facturación.

<Note>
  **Un cobro con varios medios, no pagos parciales.** Si repartís la cuenta entre efectivo y
  tarjeta, mandá las dos piezas **en la misma llamada**. Fire no acumula pagos a lo largo del
  tiempo: el cobro llega entero o no llega. Consolidá los parciales de tu lado antes de enviarlos.
</Note>

## Autenticación

<ParamField header="x-api-key" type="string" required>
  Tu API key de Fire con scope `orders:write`. La key **debe ser vendor-scoped** — las keys sin
  `vendorId` se rechazan con `403`.
</ParamField>

## Path params

<ParamField path="orderId" type="string" required>
  Cualquiera de las tres referencias públicas de la orden:

  | referencia | qué es |
  | --- | --- |
  | `orders.id` | el UUID interno de Fire |
  | `order_external` | el id que asignaste al crear la orden |
  | `metadata.order_id` | copia del id externo dentro de la orden |

  Es el mismo conjunto que aceptan [Obtener orden](/es/api-reference/get-order) y
  [Cancelar orden](/es/api-reference/cancel-order).
</ParamField>

## Cuerpo

<ParamField body="payments" type="object[]" required>
  Los medios con los que cobraste la orden. Entre 1 y 20 piezas. Cada objeto se guarda tal cual lo
  enviaste; abajo solo están los campos que Fire lee.
</ParamField>

<ParamField body="payments[].details.transaction_status" type="string" required>
  Estado del intento. Cuentan como **cobrado**: `APPROVED`, `AUTHORIZED`, `CAPTURED`, `PAID`,
  `SUCCESS`, `SUCCEEDED` (sin distinguir mayúsculas).

  Cualquier otro valor se trata como **rechazo**, incluso si no lo reconocemos. Es deliberado:
  facturar un cobro que no ocurrió no tiene vuelta atrás, mientras que no saldar algo que sí se
  cobró se resuelve con otro envío.
</ParamField>

<ParamField body="payments[].details.transaction_id" type="string" required>
  Identificador de la transacción. **Es la clave de idempotencia**: reenviar el mismo no vuelve a
  cobrar ni a facturar. Si tu medio no lo genera, Fire usa `payments[].uid`.
</ParamField>

<ParamField body="payments[].details.total_bill" type="number" required>
  Monto de esta pieza, decimal. Debe ser mayor que cero.
</ParamField>

<ParamField body="payments[].details.currency_code" type="string" required>
  Moneda de la pieza. Todas las piezas **aprobadas** deben compartir la misma.
</ParamField>

<ParamField body="payments[].details.decline_reason" type="string">
  Motivo del rechazo. Solo aplica cuando `transaction_status` no es aprobado. Los códigos
  reconocidos están en [Motivos de rechazo](/es/api-reference/payment-decline-reasons) — se aceptan
  también los códigos crudos de tu adquirente (`51`, `do_not_honor`, …).
</ParamField>

<ParamField body="payments[].method" type="string">
  Medio de pago (`CASH`, `CREDIT`, `DEBIT`, `PIX`…). Se usa para la facturación y las métricas.
</ParamField>

## Qué hace Fire con lo que enviás

Solo las piezas **aprobadas** suman y saldan. Las rechazadas se registran para tus métricas, no
suman y nunca bloquean el cobro.

| situación | `outcome` | ¿salda? |
| --- | --- | --- |
| hay aprobadas y la orden está abierta | `settled` | sí — pasa a `COMPLETED` y arranca la facturación |
| hay aprobadas y la orden **no** está abierta | `recorded` | no — se registran sin cambiar la orden |
| ninguna pieza aprobada | `declined` | no — la orden sigue abierta |
| ninguna pieza nueva (ya las habías enviado) | `duplicate` | no — reintento idempotente |

<Warning>
  **Si la suma no coincide con el total de la orden, Fire salda igual** y marca la diferencia en la
  respuesta (`amountMismatch`). Rechazar dejaría la orden abierta para siempre y la factura no
  saldría nunca: vos sos la autoridad sobre lo que cobraste. Revisá esa bandera en tu conciliación.
</Warning>

## Qué pasó con cada rechazo

Cada pieza rechazada vuelve en `declines[]`, con el motivo tal como lo enviaste y el código del
catálogo al que resolvió.

```jsonc
"declines": [
  { "sent": "51",     "resolvedTo": "INSUFFICIENT_FUNDS", "group": "funds", "retryable": false },
  { "sent": "XYZ-99", "resolvedTo": null,                 "group": null,    "retryable": null }
]
```

`resolvedTo: null` quiere decir que ese código **no matcheó ningún alias** del catálogo. El rechazo
se registró igual y el texto original quedó guardado, pero esos registros no aparecen en nada
agrupado por motivo.

<Warning>
  Revisá este bloque la primera vez que integres. Si tu adquirente usa códigos que no reconocemos,
  todos tus rechazos van a entrar sin clasificar y tu tablero de motivos va a quedar vacío — sin que
  nada falle. Cuando veas un `resolvedTo: null` recurrente, pedinos que agreguemos ese alias.
</Warning>

## Idempotencia

Cada pieza se identifica por su `transaction_id` dentro de la orden. Podés reintentar sin miedo:

- **Reenviar el cobro completo** → `duplicate`. No se vuelve a saldar ni a facturar.
- **Reenviar después de un timeout** que dejó el cobro a medias → entra solo lo que falta.

## Validaciones

Todas devuelven `400` salvo donde se indique.

| regla | código |
| --- | --- |
| `payments` con al menos una pieza | `400` |
| máximo 20 piezas | `400` |
| `details.transaction_status` presente | `400` |
| `transaction_id` o `uid` presente | `400` |
| `transaction_id` sin repetir dentro del mismo envío | `400` |
| monto mayor que cero en cada pieza | `400` |
| una sola moneda entre las piezas aprobadas | `400` |
| API key válida | `401` |
| scope `orders:write` y key vendor-scoped | `403` |
| la orden existe dentro de tu vendor | `404` |
| la referencia matchea más de una orden | `409` |

Los campos que Fire no conoce **se aceptan y se guardan**: podés enviar tu objeto de pago completo
sin recortarlo. La moneda de una pieza rechazada no invalida el envío, porque no suma.
