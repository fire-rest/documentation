Inyecta en Fire una orden que llega desde **X-MART Gateway**. Es el adapter dedicado a ese
integrador: el cuerpo es el mismo, en formato Fire, que el de
[Crear orden (v1)](/es/api-reference/create-order), y la orden pasa por el mismo núcleo: mismas
validaciones, mismo día de negocio, mismos impuestos, mismo documento fiscal y mismos
[eventos](/es/events/overview).

Lo que cambia respecto de `create-order`:

- **La tienda sale del cuerpo.** Fire la busca por `store.code` + `store.vendorId`. La ruta no
  lleva el código de tienda, aunque cuelga de `/stores/`.
- **La cuenta se resuelve desde la tienda**, no desde la API key ni desde el `accountId` del
  cuerpo.
- **El canal numérico legacy se traduce.** Si la orden no trae `channel.code` pero sí `channelId`
  (el id numérico con el que X-MART junta canal y servicio), Fire lo traduce a canal + servicio.
  Si no lo reconoce, la orden se crea igual.
- **La respuesta `201` trae `_adapter: "xmart"`.**

## Autenticación

<ParamField header="x-api-key" type="string" required>
  Tu API key de Fire (`pk_live_...`) con scope `orders:write`. También se acepta
  `Authorization: Bearer pk_live_...`; si llegan los dos, gana `x-api-key`. La key **debe estar
  asociada a una cuenta y a un vendor**: una key sin cuenta se rechaza con `403`.
</ParamField>

<ParamField header="Content-Type" type="string" required>
  `application/json`.
</ParamField>

## Cuerpo

El cuerpo es el JSON de la orden, **sin envoltura** (no `{ "payload": { ... } }`). Los montos van
como números decimales (`22.9`). Los campos que no figuran en esta página no provocan error.

### Canal y servicio

La fuente principal es `channel.code` para el canal y `service.code` para el servicio. Si falta
`channel.code` y llega `channelId`, Fire traduce ese id numérico a canal + servicio según la
configuración de canales de Fire. Si no hay `channel.code`, ni `channelId` reconocido, el canal
sale de `channelName`; y si no hay `service.code`, el servicio sale de lo traducido o de
`selectedShippingMethod`.

La resolución del canal **nunca rechaza la orden**: un `channelId` que Fire no reconoce no es un
error.

**Un PIX** va como `method: "DIGITAL"` + `processor: "PIX"`:

```json
{ "method": "DIGITAL", "processor": "PIX", "currencyCode": "BRL", "transactionStatus": "APPROVED", "totalBill": 22.9, "changeAmount": 0 }
```

**Descuento del agregador.** Una entrada con `paymentMethodCode: "AGGREGATOR_DISCOUNT"` no es un
pago real: es un descuento que financia el agregador (por ejemplo iFood). Va en
`paymentMethods[]` junto a los pagos reales y su `totalBill` cuenta en la suma de pagos; queda
fuera del cierre de caja y del documento fiscal.

**Efectivo.** En un pago `CASH` con `customerCashAmount`, el efectivo entregado tiene que cubrir
la cuenta y `changeAmount` tiene que ser la diferencia.

### Datos fiscales

Los datos del comprador para el documento fiscal salen de `client.billingInformation` y, si ahí
no están, de `client`:

| Clave de `billingInformation` | Uso |
|---|---|
| `govIdType` | Tipo de documento. Tiene prioridad sobre `client.govIdType` |
| `govIdNumber` | Número de documento. Tiene prioridad sobre `client.govIdNumber` |
| `name`, luego `businessName` | Nombre. Si falta, `client.name` + `client.lastName` |
| `email` | Correo. Si falta, `client.email` |
| `address` | Dirección |

El teléfono sale solo de `client.phone`.

**Consumidor final.** Si el tipo es `FINAL_CONSUMER` o el documento no es válido —en Brasil, CPF o
CNPJ de 11 o 14 dígitos; en los demás países, entre 6 y 13 caracteres alfanuméricos—, Fire trata
al comprador como consumidor final y descarta lo que vino del canal (`CONSUMIDOR`,
`00000000000`, correos genéricos). Si la cuenta tiene configurados datos de consumidor final,
Fire usa esos.

## Estado de la orden

El `transactionStatus` de los pagos (sin distinguir mayúsculas) decide el estado con que nace la
orden y qué evento sale:

| `transactionStatus` de los pagos | `status` | `payment_status` | Evento |
|---|---|---|---|
| Todos `APPROVED` | `COMPLETED` | `SUCCEEDED` | [`order.completed`](/es/events/order-completed) |
| Alguno `REJECTED`, `FAILED` o `CANCELLED` | `OPEN` | `FAILED` | [`order.opened`](/es/events/order-opened) |
| Otro (`PENDING`, `AUTHORIZED`…) | `OPEN` | `PENDING` | [`order.opened`](/es/events/order-opened) |

Solo `APPROVED` aprueba: un pago `AUTHORIZED` deja la orden abierta. Toda orden nueva dispara
exactamente uno de los dos eventos. Si el evento no se puede encolar, la orden se crea igual.

## Duplicados

La clave de duplicados es **`orderId` + `store.vendorId`**. Si reenvías una orden que ya entró, la
respuesta es `409` con `code: "DUPLICATE_ORDER"` y `data` trae `id`, `externalOrderId` y `status`
de la orden existente. **Trátalo como "ya ingerida", no como una falla:** no se reescribe la orden
ni se vuelven a emitir eventos.

El mismo `orderId` con otro `store.vendorId` es otra orden. No hay header `Idempotency-Key`.

<Note>
  Las reglas de validación de la orden corren antes del chequeo de duplicado. Si una orden entró
  cuando una regla todavía no rechazaba y la reenvías después de que se active, recibes el `400`
  de esa regla en lugar del `409`.
</Note>

## Numeración fiscal en la inyección

<Note>
  **Apagada por defecto.** Se prende por vendor en la configuración fiscal de Fire, cuando tus
  cajas ya leen el bloque `fiscal` de abajo. Hasta entonces no cambia nada: sigues numerando con
  [`POST /fiscal/numbering`](/es/api-reference/fiscal-documents-v2) antes de inyectar, y la
  respuesta trae `fiscal: null`.
</Note>

Prendida, Fire numera la venta **dentro de este mismo request**: no llamas antes a
`POST /fiscal/numbering`. La inyección puede tardar hasta unos 5 s más (la espera al proveedor):
dale a tu cliente HTTP un timeout holgado. Acá se numeran solo las ventas que nacen cobradas (`COMPLETED` /
`SUCCEEDED`); una orden que nace `OPEN` se numera cuando se cobra, en
[Confirmar pago](/es/api-reference/confirm-payment#numeración-fiscal-al-cobrar).

Lo que va al proveedor fiscal Fire lo arma con la orden que inyectas, igual que lo arma tu caja para
`POST /fiscal/numbering`: el comprador sale de `client` (y `billingInformation`), los montos de
`payments.totals` y la caja de `device` — **`device.uid` es obligatorio** (sin él: `FISCAL_DEVICE_MISSING`). El número se guarda con la
orden, así que [`order.completed`](/es/events/order-completed) ya trae `fiscalRepresentation`.

La respuesta trae un bloque `fiscal`. **Lee primero `fiscal.action`:**

| `fiscal.action` | Qué significa | Qué hace tu caja |
|---|---|---|
| `CONTINUE` | La orden se creó. Con `requestStatus: GENERATED` está numerada; con cualquier otro estado se creó sin número | Sigue con la venta |
| `REFUND` | La numeración falló y la política del vendor es devolver. **La orden no se creó**: la respuesta es un `400` (ver [Errores](#errores)) | Devuelve el dinero y reporta la [venta perdida](/es/api-reference/lost-sales#si-tu-vendor-numera-en-la-inyección) con `reason: "FISCAL_NUMBERING_FAILED"`. No reenvía la orden |

`REFUND` solo pasa si el vendor configuró esa política; la que rige por defecto es `CONTINUE`.
`fiscal.failure.message` es el texto para mostrarle al cajero. Los mensajes que escribe Fire vienen
en español; un error de configuración trae el mensaje técnico. Decide por `failure.code`, no por el
texto:

| `failure.code` | `requestStatus` | Cuándo |
|---|---|---|
| `FISCAL_DEVICE_MISSING` | `FAILED_FINAL` | La orden no trae `device.uid`. Fire no llama al proveedor |
| `FISCAL_CONFIGURATION_ERROR` | `FAILED_FINAL` | La configuración fiscal de la tienda o del vendor está incompleta o mal. Reintentar no lo arregla |
| `FISCAL_NUMBERING_ERROR` | `FAILED_RETRYABLE` | Un error pasajero del lado de Fire, por ejemplo otra petición numerando la misma venta |
| `PROVIDER_TIMEOUT` | `PENDING` | El proveedor no contestó a tiempo. Pudo haber numerado |
| `PROVIDER_UNREACHABLE` | `PENDING` | No hubo conexión con el proveedor |
| `PROVIDER_UNAVAILABLE` | `FAILED_RETRYABLE` | El proveedor contestó `5xx`, o Fire dejó de llamarlo (ver abajo) |

Otros códigos vienen del proveedor (por ejemplo, un rechazo por las reglas de la autoridad
tributaria). En todos los casos decide la política del vendor.

**Si el proveedor está caído o lento.** Fire espera al proveedor como máximo el tiempo configurado
para el vendor: 2,8 s por defecto, **nunca más de 5 s**. Un proveedor que no contesta a tiempo da
`requestStatus: PENDING` — pudo haber numerado. Después de 5 fallas de infraestructura seguidas (sin
respuesta, `5xx`, `408` o `429`), Fire deja de llamar al proveedor de ese vendor durante 30 segundos y
contesta enseguida con `FAILED_RETRYABLE` y `failure.code: PROVIDER_UNAVAILABLE`, para que un
proveedor caído no frene cada venta. Después una sola venta prueba al proveedor; si contesta, la
numeración vuelve. La cuenta la lleva cada servidor de Fire, así que en una caída el proveedor puede
recibir más de 5 llamadas y más de una venta de prueba. En todos los casos decide la política del vendor: con `CONTINUE`, la orden se crea
sin número.

**Si ya numeraste.** Una caja que numeró con `POST /fiscal/numbering` y después inyecta con el mismo
`orderCode` no se numera dos veces: Fire reusa ese documento y contesta `CONTINUE`.

**Duplicados.** La numeración queda atada al `orderId`. El mismo `orderId` con otro `orderCode` no se
vuelve a numerar: si la orden existe recibes el `409` de siempre; si no existe, es una falla de
numeración (`FISCAL_IDEMPOTENCY_CONFLICT`) que resuelve la política.

## Errores

Todo error trae `success: false`, `error` (la categoría) y `message`; algunos traen `code`, `data`
o `details`. Este endpoint **no responde `422`**: los rechazos de negocio son `400`
`BUSINESS_ERROR`.

| HTTP | `error` / `code` | Cuándo |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Falta `orderCode` o viene vacío; también con cuerpo vacío o JSON inválido. `message`: `orderCode is required and must be a non-empty string` |
| `400` | `VALIDATION_ERROR` | El cuerpo no tiene el formato. `details` lista cada problema con su `path` |
| `401` | `UNAUTHORIZED` | Falta la API key, no empieza con `pk_live_`, o está vencida o revocada |
| `403` | `FORBIDDEN` | API key sin scope `orders:write`, o no asociada a una cuenta |
| `404` | `NOT_FOUND` | No hay tienda con ese `store.code` + `store.vendorId`. `message`: `Store not found with ID <code>` |
| `400` | `BUSINESS_ERROR` | Tienda inactiva o no publicada. `message`: `Store <code> is not active or not published. …` |
| `400` | `BUSINESS_ERROR` | Día de negocio cerrado. `message`: `Store <code> business day is not open. …` |
| `400` | `BUSINESS_ERROR` + `details.code: ORDER_INVARIANT_VIOLATION` | La orden no cumple una regla de validación activada para tu vendor. Ver abajo |
| `409` | `CONFLICT` / `DUPLICATE_ORDER` | La orden ya existía para ese vendor. Ver [Duplicados](#duplicados) |
| `400` | `DOMAIN_ERROR` o `BUSINESS_ERROR` con `message` que empieza por `Failed to` | Falla interna de Fire, no de tu orden |
| `503` | `SERVICE_UNAVAILABLE` | No se pudo verificar la API key en ese momento |
| `500` | `INTERNAL_SERVER_ERROR` | Error inesperado |
| `400` | `BUSINESS_ERROR` + `details.code: FISCAL_NUMBERING_FAILED` | Solo con numeración en la inyección: la numeración falló y la política del vendor es `REFUND`. `details.fiscal` trae el bloque. La orden no se creó |

### Rechazo por reglas de validación

Cada vendor puede activar, por canal, reglas que revisan la orden antes de guardarla. Una orden que
pasa la validación del formato puede igual rechazarse aquí. El rechazo no agrega claves a la raíz:
todo lo nuevo va en `details`.

| `details.violations[].category` | Qué pasó |
|---|---|
| `TAX_MISSING` | Un producto o modificador con precio no trae impuestos |
| `TAX_MALFORMED` | Impuestos incompletos (sin `name`, `rate`, `amount` o `base`), que no suman el total de impuestos, o el mismo impuesto escrito de dos formas |
| `ORDER_NOT_BALANCED` | Los productos no suman el total de la orden |
| `PRODUCT_NOT_MAPPED` | Un producto sin `additionalInfo.externalCode` |
| `CASH_CHANGE_INVALID` | Un pago en efectivo con el vuelto incoherente |
| `PRODUCT_TYPE_MISMATCH` | Un producto o modificador enviado con un `type` distinto al del menú sincronizado, o sin `type`. Con la regla activada, uno sin `type` se rechaza siempre, esté o no en el catálogo. `expected` es el tipo del menú, o `null` si no enviaste `type` y el tipo resultante es `PRODUCT` (menú `PRODUCT` o producto fuera del catálogo); `received`, el que enviaste, o `""` si no enviaste ninguno |

Cada violación trae `invariant`, `category` (estable, para automatizar), `path` (la ruta dentro del
cuerpo que enviaste, como `order.products[0]`), `expected` y `received` (decimales en las reglas de montos; nombres de tipo en `PRODUCT_TYPE_MISMATCH`, donde `expected` puede ser `null`), y `message`.
En `ORDER_NOT_BALANCED`, `lines` dice cuánto suma cada producto.

<Note>
  Pasar la validación del formato no garantiza que la orden se acepte. El ejemplo de esta página no
  trae `taxes[]` por producto: con la regla de impuestos activada para tu vendor, se rechazaría con
  `TAX_MISSING`.
</Note>

```json
{
  "success": false,
  "error": "BUSINESS_ERROR",
  "message": "Order rejected — 1 problem. [I6] order.products: the products add up to 73.70 but the order total is 75.70 (difference 2.00). A product, an option or a price is missing.",
  "details": {
    "code": "ORDER_INVARIANT_VIOLATION",
    "orderCode": "AGG-KEETA-K066-…",
    "externalOrderId": "…",
    "violations": [
      { "invariant": "I6", "category": "ORDER_NOT_BALANCED", "path": "order.products", "expected": "75.70", "received": "73.70",
        "message": "…", "lines": [{ "path": "order.products[0]", "externalCode": "30033", "name": "…", "total": "73.70" }] }
    ]
  }
```

### Rechazo por la numeración fiscal

Solo con [numeración en la inyección](#numeración-fiscal-en-la-inyección) y la política `REFUND`.
El mismo sobre que las reglas de validación: todo va en `details`.

```json
{
  "success": false,
  "error": "BUSINESS_ERROR",
  "message": "Could not number the sale",
  "details": {
    "code": "FISCAL_NUMBERING_FAILED",
    "orderCode": "…",
    "externalOrderId": "…",
    "fiscal": {
      "action": "REFUND",
      "requestStatus": "FAILED_RETRYABLE",
      "failure": { "code": "PROVIDER_UNAVAILABLE", "message": "…" }
    }
  }
}
```

### Cuándo reintentar

| Respuesta | Qué hacer |
|---|---|
| `201` | Nada. |
| `409` `DUPLICATE_ORDER` | **No reintentar**: la orden ya está. Usar `data.id`. |
| `400` con `details.code: FISCAL_NUMBERING_FAILED` | **No reenviar**: devolver el dinero y reportar la [venta perdida](/es/api-reference/lost-sales#si-tu-vendor-numera-en-la-inyección) con `reason: "FISCAL_NUMBERING_FAILED"` y `details.fiscal.failure` en `detail`. |
| `400` `VALIDATION_ERROR`, `400` con `ORDER_INVARIANT_VIOLATION`, `401`, `403`, `404` | Corregir y reenviar con el mismo `orderId`. Un reintento idéntico falla igual. |
| `400` `BUSINESS_ERROR` por tienda inactiva o día cerrado | Reintentar cuando cambie el estado. Tras abrir el día, la tienda puede tardar hasta 30 segundos en aceptar órdenes. |
| `400` con `message` que empieza por `Failed to`, `503`, `500` | Reintentar con backoff. Es seguro: si la orden ya había entrado, la respuesta es `409`. |

<Info>
  Toda petición autenticada queda registrada en Fire con su cuerpo y su resultado, también las
  rechazadas.
</Info>
