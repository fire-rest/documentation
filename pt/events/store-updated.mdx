<Note>
  **Disponibilidade limitada.** Este evento está em implantação e é habilitado por conta. Consulte seu contato no Fire para saber se já se aplica à sua.
</Note>

<Warning>
  Este é o evento `store.updated` de **Integration Flows**, documentado nesta página. **Não** é o webhook de integrações de agregadores com o mesmo nome descrito em [Referência de webhooks → `store.updated`](/pt/webhook-reference/store-updated): aquele pertence a outro sistema, tem outro formato e não muda.
</Warning>

`store.updated` é disparado toda vez que a configuração de uma loja é **publicada** nos seus canais: primeira publicação, publicar um rascunho, ressincronizar, ligar ou desligar um canal, aplicar um override, arquivar. Ele sempre traz a **loja completa** — nunca um diff. Trate-o como uma substituição total do que você sabe sobre essa loja.

Assim como `store.business_day_closed`, é um evento **no nível da loja**: um por publicação, não um por pedido nem por canal. Uma publicação que envolve vários canais gera um único evento com todos os canais dentro, e cada flow que a recebe recebe esse evento uma única vez, com a loja completa.

## Condição de disparo

Cada publicação de uma loja emite **um** `store.updated`. `data.publication.reason` diz o que o gerou:

| `reason` | O que aconteceu |
|---|---|
| `publish` | A loja foi publicada pela primeira vez (também quando uma loja é criada já publicada). |
| `draft` | As mudanças pendentes de uma loja publicada foram aplicadas. Os canais que são desligados viajam com `enabled: false`. |
| `resync` | Alguém ressincronizou a loja; ela viaja exatamente como está. |
| `channel_toggle` | Um canal da loja foi ligado ou desligado, manualmente ou pelo seu horário. |
| `override_apply` / `override_revert` | Um override foi aplicado à loja, ou revertido. |
| `archive` | A loja foi arquivada — veja [Arquivar](#arquivar). |

Podem aparecer valores novos de `reason` (o contrato já admite `retry`) e de `mode`. Trate um valor que você não conhece como uma publicação normal: o evento continua trazendo a loja completa.

Uma publicação também pode ser **agendada**: ao agendá-la nada é emitido; o evento é disparado quando chega a hora agendada, com `publication.mode: "scheduled"` e `publication.scheduledAt`. Cancelar uma publicação agendada não emite nada.

**Nada é emitido** quando mudanças são salvas sem publicá-las nos canais, nem quando o dia de negócio abre ou fecha.

| | |
|---|---|
| Cobertura | Todos os países, nas contas onde o evento está habilitado |
| Id da publicação | `data.publication.id` — o mesmo em cada entrega e em cada flow que recebe essa publicação |
| Id da entrega | `event.id`, como em todos os eventos (a execução do flow) |
| Ordem | `data.publication.sequence`, por loja — veja [A publicação mais recente vence](#a-publicação-mais-recente-vence) |
| Entidade | `_meta.triggerEntityId` é o UUID da loja (`data.store.uid`) |

<Note>
  Um flow limitado a certos canais recebe uma publicação quando ela envolve **pelo menos um** deles — e recebe o evento **completo**, com todos os canais. Escolha os que são seus em `data.channels`.
</Note>

## Referência de `data.*`

### `data.store`

<ResponseField name="store" type="object">
  O **mesmo bloco de loja V4** que viaja nos eventos de pedido — `uid`, `code`, `name`, `phone`, `email`, `address`, `externalId`, `vendor`, `account`, `locationInfo` (com `country.phoneCode`), `metadata` e `storeFiscalConfig` (pode ser `null`). Referência de campos em [`order.completed` → `data.store`](/pt/events/order-completed#data-store). `phone` vem em formato internacional (`+` e dígitos, p. ex. `+5511999990000`). Pode trazer um número que não é real (por exemplo, só zeros) se a loja não tem telefone cadastrado, ou o valor como foi salvo se o país não tem código telefônico. `metadata` é a configuração **chave-valor livre** da loja: o Fire não impõe as chaves, algumas integrações leem chaves conhecidas (no exemplo, `taxesInfo` e `deliveryInfo`), e é `{}` quando a loja não tem nenhuma. Sobre esse bloco, este evento acrescenta:

  <Expandable title="campos que store.updated acrescenta">
    <ResponseField name="number" type="integer | null">
      O número sequencial da loja no Fire. `null` quando não é conhecido.
    </ResponseField>
    <ResponseField name="status" type="string">
      Estado de publicação da loja: `DRAFT`, `PUBLISHED`, `PARTIALLY_PUBLISHED` ou `ARCHIVED`.
    </ResponseField>
    <ResponseField name="active" type="boolean">
      Se a loja está ativa. Sempre `false` quando arquivada.
    </ResponseField>
  </Expandable>
</ResponseField>

### `data.channels`

<ResponseField name="channels" type="array">
  **Todos** os canais configurados na loja — não só os desta publicação (esses estão em `publication.channels`). Um canal ou tipo de serviço desligado viaja do mesmo jeito, com `enabled: false`: é assim que você fica sabendo que ele saiu do ar.

  <Expandable title="channels[]">
    <ResponseField name="code" type="string">
      Código do canal, escrito como está configurado no Fire (`KIOSK`, `POS`, `iFood`, `99`, …). Compare sem assumir maiúsculas ou minúsculas.
    </ResponseField>
    <ResponseField name="enabled" type="boolean">
      Se o canal está habilitado na loja.
    </ResponseField>
    <ResponseField name="published" type="boolean">
      Se o canal está entre os canais publicados da loja.
    </ResponseField>
    <ResponseField name="fulfillmentTypes" type="array">
      Os tipos de serviço do canal.
      <Expandable title="fulfillmentTypes[]">
        <ResponseField name="code" type="string">Código do tipo de serviço (`DELIVERY`, `TAKEAWAY`, `DINE_IN`, …).</ResponseField>
        <ResponseField name="enabled" type="boolean">Se o tipo de serviço está habilitado neste canal.</ResponseField>
        <ResponseField name="schedules" type="array">
          O horário **efetivo**, já resolvido: o horário próprio do tipo de serviço; se não tiver, o do canal; se o canal também não tiver, o `salesSchedule` da loja. Cada entrada é `{ day, startTime, endTime }`, no mesmo formato de abaixo. Você não precisa aplicar a herança.
        </ResponseField>
      </Expandable>
    </ResponseField>
  </Expandable>
</ResponseField>

### `data.operationSchedule` e `data.salesSchedule`

<ResponseField name="operationSchedule" type="array">
  O horário de operação da loja. Cada entrada: `day` (`MONDAY` … `SUNDAY`), `startTime` e `endTime` (`HH:mm`).
</ResponseField>
<ResponseField name="salesSchedule" type="array">
  O horário de venda da loja, no mesmo formato. É o padrão para canais e tipos de serviço sem horário próprio — já aplicado em `channels[].fulfillmentTypes[].schedules`.
</ResponseField>

### `data.salesGoals`

<ResponseField name="salesGoals" type="object">
  As metas de venda da loja: a meta do **mês atual e dos meses futuros**, já distribuída por dia. Valores de **venda líquida, sem impostos**, na moeda da loja. Só vem quando a loja tem metas cadastradas; caso contrário, o campo não aparece. Só viaja em `store.updated`, em nenhum outro evento.

  <Expandable title="salesGoals">
    <ResponseField name="version" type="integer">Versão do formato. Hoje `2`.</ResponseField>
    <ResponseField name="currency" type="string">Moeda dos valores (ISO 4217, ex. `BRL`).</ResponseField>
    <ResponseField name="months" type="array">
      Um item por mês com meta, em ordem.

      <Expandable title="months[]">
        <ResponseField name="month" type="string">Mês, `YYYY-MM`.</ResponseField>
        <ResponseField name="amount" type="number">Meta do mês. É a soma de `days[].amount`.</ResponseField>
        <ResponseField name="distribution" type="string">Como foi distribuída por dia: `HISTORY` (pelo quanto a loja vende em cada dia da semana) ou `EVEN` (igual).</ResponseField>
        <ResponseField name="weights" type="number[]">Opcional. Os 7 pesos usados, de segunda a domingo.</ResponseField>
        <ResponseField name="days" type="array">Todos os dias do mês: `date` (`YYYY-MM-DD`), `amount` (meta do dia, 2 decimais) e `fixed` (`true` se foi definida à mão; `amount: 0` com `fixed: true` = dia fechado).</ResponseField>
        <ResponseField name="updatedAt" type="string">Quando a meta desse mês foi alterada (ISO 8601, UTC).</ResponseField>
        <ResponseField name="updatedBy" type="object">Quem alterou: `{ id, name }`.</ResponseField>
      </Expandable>
    </ResponseField>
  </Expandable>
</ResponseField>

A meta da semana é a soma dos seus dias. A meta por hora não viaja: se precisar, distribua a meta do dia pelo seu próprio perfil horário.

### `data.publication`

<ResponseField name="publication" type="object">
  A publicação que gerou este evento.

  <Expandable title="publication">
    <ResponseField name="id" type="string">
      UUID da publicação. O mesmo em cada entrega e em cada flow que a recebe — use-o para reconhecer uma publicação que você já aplicou.
    </ResponseField>
    <ResponseField name="sequence" type="integer">
      Contador por loja: sobe em um a cada publicação emitida daquela loja. A maior é a mais nova. Veja [A publicação mais recente vence](#a-publicação-mais-recente-vence).
    </ResponseField>
    <ResponseField name="mode" type="string">
      `now` (publicada na hora) ou `scheduled` (disparada por um agendamento). Podem aparecer valores novos; trate-os como uma publicação normal.
    </ResponseField>
    <ResponseField name="reason" type="string">
      O que gerou a publicação: `publish`, `draft`, `resync`, `channel_toggle`, `override_apply`, `override_revert` ou `archive`. Podem aparecer valores novos (p. ex. `retry`); trate-os como uma publicação normal. Veja [Condição de disparo](#condição-de-disparo).
    </ResponseField>
    <ResponseField name="channels" type="string[]">
      Os códigos de canal de que trata esta publicação: os escolhidos ao publicar, todos os canais habilitados numa ressincronização, o canal ligado ou desligado num `channel_toggle`, o canal pontual numa ressincronização de um só canal, todos os canais habilitados num `override_apply` ou `override_revert`, e ao arquivar, os canais publicados mais os habilitados.
    </ResponseField>
    <ResponseField name="scheduledAt" type="string | null">
      Hora ISO 8601 UTC para a qual a publicação foi agendada. `null` quando `mode` é `now`.
    </ResponseField>
    <ResponseField name="requestedBy" type="object">
      `{ id, name }` — quem a pediu. Qualquer um dos dois pode ser `null`; execuções automáticas podem chegar com `id: null` e `name: "CRON"`.
    </ResponseField>
  </Expandable>
</ResponseField>

## A publicação mais recente vence

Cada evento traz a loja **completa**, então a publicação mais recente substitui tudo o que veio antes. O Fire já cuida da ordem para você:

- Dentro de um flow, as publicações de **uma mesma loja** são entregues uma por vez, na ordem em que foram emitidas. Lojas diferentes avançam em paralelo.
- Quando uma loja recebe uma publicação nova que cobre os mesmos canais, as entregas anteriores que ainda estavam esperando são canceladas; as demais saem do mesmo jeito, em ordem.

`publication.sequence` continua sendo um dado útil: você pode guardar a última que aplicou por loja e reconhecer um payload antigo se algum dia ele chegar — por exemplo, uma reexecução manual de uma entrega antiga, que mantém sua `sequence` original.

## Arquivar

Arquivar uma loja emite um `store.updated` com `publication.reason: "archive"`. Ele traz a loja arquivada: `store.status: "ARCHIVED"`, `store.active: false`, e **todos** os canais e tipos de serviço com `enabled: false` (e os canais com `published: false`). Se quiser tratar o arquivamento à parte, ramifique por `reason` ou por `status`.

<Note>
  Integration Flows não emite um evento `store.deleted` separado: arquivar é um `store.updated`.
</Note>

## Exemplo de handler

```js
async function onStoreUpdated(data) {
  const { store, channels, publication } = data;

  // 1. Já aplicamos esta publicação? (mesmo id em cada entrega)
  if (await db.storePublications.exists(publication.id)) return;

  // 2. Opcional: guardar a sequence para reconhecer um payload antigo
  const last = await db.stores.lastSequence(store.uid);
  if (last != null && publication.sequence < last) return;

  // 3. Substituição total — o evento traz a loja completa
  const mine = channels.filter((c) => MY_CHANNELS.includes(c.code.toUpperCase()));
  await db.stores.replace(store.uid, {
    code: store.code,
    name: store.name,
    active: store.active,
    archived: store.status === "ARCHIVED",
    metadata: store.metadata,
    channels: mine,
    sequence: publication.sequence,
  });
  await db.storePublications.add(publication.id);
}
```

## Erros comuns

- **Não é um diff.** Um canal que falta na sua cópia não está "sem mudanças" — o evento lista todos os canais. Substitua, não mescle.
- **Um canal desligado viaja do mesmo jeito.** Leia `enabled`; não assuma que um canal presente no evento está aberto.
- **`publication.channels` não é a lista de canais.** Diz do que tratou esta publicação; os canais da loja estão em `data.channels`.
- **Não deduplique por `event.id`.** Ele identifica a entrega; a publicação é `data.publication.id`.
- **Os códigos de canal mantêm as maiúsculas com que foram configurados** (`iFood`, `KIOSK`). Normalize antes de comparar.
