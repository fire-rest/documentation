Injeta no Fire um pedido que chega do **X-MART Gateway**. É o adapter dedicado a esse integrador:
o corpo é o mesmo, no formato Fire, que o de [Criar pedido (v1)](/pt/api-reference/create-order),
e o pedido passa pelo mesmo núcleo: mesmas validações, mesmo dia de negócio, mesmos impostos,
mesmo documento fiscal e mesmos [eventos](/pt/events/overview).

O que muda em relação a `create-order`:

- **A loja vem do corpo.** O Fire a busca por `store.code` + `store.vendorId`. A rota não leva o
  código da loja, embora fique sob `/stores/`.
- **A conta é resolvida a partir da loja**, não a partir da API key nem do `accountId` do corpo.
- **O canal numérico legado é traduzido.** Se o pedido não traz `channel.code` mas traz
  `channelId` (o id numérico com que o X-MART junta canal e serviço), o Fire o traduz para canal +
  serviço. Se não o reconhecer, o pedido é criado mesmo assim.
- **A resposta `201` traz `_adapter: "xmart"`.**

## Autenticação

<ParamField header="x-api-key" type="string" required>
  Sua API key do Fire (`pk_live_...`) com escopo `orders:write`. Também é aceito
  `Authorization: Bearer pk_live_...`; se chegarem os dois, vale `x-api-key`. A key **deve estar
  associada a uma conta e a um vendor**: uma key sem conta é rejeitada com `403`.
</ParamField>

<ParamField header="Content-Type" type="string" required>
  `application/json`.
</ParamField>

## Corpo

O corpo é o JSON do pedido, **sem envelope** (não `{ "payload": { ... } }`). Os valores vão como
números decimais (`22.9`). Campos que não aparecem nesta página não causam erro.

### Canal e serviço

A fonte principal é `channel.code` para o canal e `service.code` para o serviço. Se faltar
`channel.code` e chegar `channelId`, o Fire traduz esse id numérico para canal + serviço de acordo
com a configuração de canais do Fire. Se não houver `channel.code` nem `channelId` reconhecido, o
canal vem de `channelName`; e se não houver `service.code`, o serviço vem da tradução ou de
`selectedShippingMethod`.

A resolução do canal **nunca rejeita o pedido**: um `channelId` que o Fire não reconhece não é um
erro.

**Um PIX** vai como `method: "DIGITAL"` + `processor: "PIX"`:

```json
{ "method": "DIGITAL", "processor": "PIX", "currencyCode": "BRL", "transactionStatus": "APPROVED", "totalBill": 22.9, "changeAmount": 0 }
```

**Desconto do agregador.** Uma entrada com `paymentMethodCode: "AGGREGATOR_DISCOUNT"` não é um
pagamento real: é um desconto financiado pelo agregador (por exemplo o iFood). Vai em
`paymentMethods[]` junto com os pagamentos reais e o seu `totalBill` conta na soma dos pagamentos;
fica fora do fechamento de caixa e do documento fiscal.

**Dinheiro.** Em um pagamento `CASH` com `customerCashAmount`, o dinheiro entregue tem que cobrir a
conta e `changeAmount` tem que ser a diferença.

### Dados fiscais

Os dados do comprador para o documento fiscal vêm de `client.billingInformation` e, se não
estiverem lá, de `client`:

| Chave de `billingInformation` | Uso |
|---|---|
| `govIdType` | Tipo de documento. Tem prioridade sobre `client.govIdType` |
| `govIdNumber` | Número do documento. Tem prioridade sobre `client.govIdNumber` |
| `name`, depois `businessName` | Nome. Se faltar, `client.name` + `client.lastName` |
| `email` | E-mail. Se faltar, `client.email` |
| `address` | Endereço |

O telefone vem só de `client.phone`.

**Consumidor final.** Se o tipo for `FINAL_CONSUMER` ou o documento não for válido —no Brasil, CPF
ou CNPJ de 11 ou 14 dígitos; nos demais países, entre 6 e 13 caracteres alfanuméricos—, o Fire
trata o comprador como consumidor final e descarta o que veio do canal (`CONSUMIDOR`,
`00000000000`, e-mails genéricos). Se a conta tiver dados de consumidor final configurados, o Fire
usa esses.

## Status do pedido

O `transactionStatus` dos pagamentos (sem diferenciar maiúsculas) decide o status com que o pedido
nasce e qual evento sai:

| `transactionStatus` dos pagamentos | `status` | `payment_status` | Evento |
|---|---|---|---|
| Todos `APPROVED` | `COMPLETED` | `SUCCEEDED` | [`order.completed`](/pt/events/order-completed) |
| Algum `REJECTED`, `FAILED` ou `CANCELLED` | `OPEN` | `FAILED` | [`order.opened`](/pt/events/order-opened) |
| Outro (`PENDING`, `AUTHORIZED`…) | `OPEN` | `PENDING` | [`order.opened`](/pt/events/order-opened) |

Só `APPROVED` aprova: um pagamento `AUTHORIZED` deixa o pedido aberto. Todo pedido novo dispara
exatamente um dos dois eventos. Se o evento não puder ser enfileirado, o pedido é criado mesmo
assim.

## Duplicados

A chave de duplicados é **`orderId` + `store.vendorId`**. Se você reenviar um pedido que já
entrou, a resposta é `409` com `code: "DUPLICATE_ORDER"` e `data` traz `id`, `externalOrderId` e
`status` do pedido existente. **Trate-o como "já ingerido", não como uma falha:** o pedido não é
reescrito e os eventos não são emitidos de novo.

O mesmo `orderId` com outro `store.vendorId` é outro pedido. Não há header `Idempotency-Key`.

<Note>
  As regras de validação do pedido rodam antes da verificação de duplicado. Se um pedido entrou
  quando uma regra ainda não rejeitava e você o reenvia depois que ela for ativada, recebe o `400`
  dessa regra em vez do `409`.
</Note>

## Numeração fiscal na injeção

<Note>
  **Desligada por padrão.** É ligada por vendor na configuração fiscal do Fire, quando os seus
  caixas já leem o bloco `fiscal` abaixo. Até lá nada muda: você continua numerando com
  [`POST /fiscal/numbering`](/pt/api-reference/fiscal-documents-v2) antes de injetar, e a resposta
  traz `fiscal: null`.
</Note>

Ligada, o Fire numera a venda **dentro desta mesma requisição**: você não chama
`POST /fiscal/numbering` antes. A injeção pode então demorar até uns 5 s a mais (a espera pelo
provedor): dê ao seu cliente HTTP um timeout folgado. Aqui só são numeradas as vendas que nascem pagas (`COMPLETED` /
`SUCCEEDED`); um pedido que nasce `OPEN` é numerado quando é cobrado, em
[Confirmar pagamento](/pt/api-reference/confirm-payment#numeração-fiscal-na-cobrança).

O que vai para o provedor fiscal o Fire monta a partir do pedido que você injeta, do mesmo jeito que
o seu caixa monta para `POST /fiscal/numbering`: o comprador sai de `client` (e `billingInformation`),
os valores de `payments.totals` e o caixa de `device` — **`device.uid` é obrigatório** (sem ele: `FISCAL_DEVICE_MISSING`). O número é
salvo com o pedido, então [`order.completed`](/pt/events/order-completed) já traz
`fiscalRepresentation`.

A resposta traz um bloco `fiscal`. **Leia primeiro `fiscal.action`:**

| `fiscal.action` | O que significa | O que o seu caixa faz |
|---|---|---|
| `CONTINUE` | O pedido foi criado. Com `requestStatus: GENERATED` está numerado; com qualquer outro status foi criado sem número | Segue com a venda |
| `REFUND` | A numeração falhou e a política do vendor é devolver. **O pedido não foi criado**: a resposta é um `400` (ver [Erros](#erros)) | Devolve o dinheiro e informa a [venda perdida](/pt/api-reference/lost-sales#se-o-seu-vendor-numera-na-injeção) com `reason: "FISCAL_NUMBERING_FAILED"`. Não reenvia o pedido |

`REFUND` só acontece se o vendor configurou essa política; a padrão é `CONTINUE`.
`fiscal.failure.message` é o texto para mostrar ao operador de caixa. As mensagens que o Fire
escreve vêm em espanhol; um erro de configuração traz a mensagem técnica. Decida por `failure.code`,
não pelo texto:

| `failure.code` | `requestStatus` | Quando |
|---|---|---|
| `FISCAL_DEVICE_MISSING` | `FAILED_FINAL` | O pedido não traz `device.uid`. O Fire não chama o provedor |
| `FISCAL_CONFIGURATION_ERROR` | `FAILED_FINAL` | A configuração fiscal da loja ou do vendor está incompleta ou errada, ou um dado da venda não é válido para o país. Tentar de novo não resolve |
| `FISCAL_NUMBERING_ERROR` | `FAILED_RETRYABLE` | Um erro passageiro do lado do Fire, por exemplo outra requisição numerando a mesma venda |
| `PROVIDER_TIMEOUT` | `PENDING` | O provedor não respondeu a tempo. Pode ter numerado. Se respondeu `504`, vem como `FAILED_RETRYABLE` |
| `PROVIDER_CONTRACT_VIOLATION` | `PENDING` | O provedor respondeu `2xx`, mas com algo que o Fire não consegue ler. Pode ter numerado |
| `PROVIDER_UNREACHABLE` | `PENDING` | Não houve conexão com o provedor |
| `PROVIDER_UNAVAILABLE` | `FAILED_RETRYABLE` | O provedor respondeu `5xx`, `408` ou `429`, ou o Fire parou de chamá-lo (ver abaixo) |
| `PROVIDER_AUTH_FAILED` | `FAILED_FINAL` | O provedor respondeu `401` ou `403`: a credencial do vendor está errada ou foi revogada |
| `FISCAL_COUNTRY_NOT_SUPPORTED` | `FAILED_FINAL` | O provedor respondeu `404`: não atende esse país |
| `FISCAL_BUSINESS_RULE` | `FAILED_FINAL` | O provedor recusou o documento (`400` ou `422`), por exemplo pelas regras da autoridade tributária |
| `FISCAL_IDEMPOTENCY_CONFLICT` | `FAILED_FINAL` | Este `orderId` já foi numerado com outro `orderCode` e não há pedido para devolver (ver Duplicados abaixo) |

O `requestStatus` da tabela é o habitual: se o provedor diz se dá para tentar de novo, vale a
resposta dele. **Decida por `fiscal.action`**: em todos os casos manda a política do vendor.

**Se o provedor estiver fora do ar ou lento.** O Fire espera o provedor no máximo o tempo configurado
para o vendor: 2,8 s por padrão, **nunca mais de 5 s**. Um provedor que não responde a tempo dá
`requestStatus: PENDING` — pode ter numerado. Depois de 5 falhas de infraestrutura seguidas (sem
resposta, `5xx`, `408` ou `429`), o Fire para de chamar o provedor desse vendor por 30 segundos e
responde na hora com `FAILED_RETRYABLE` e `failure.code: PROVIDER_UNAVAILABLE`, para que um provedor
fora do ar não segure cada venda. Depois uma única venda testa o provedor; se ele responder, a
numeração volta. A contagem é feita por cada servidor do Fire, então numa queda o provedor pode
receber mais de 5 chamadas e mais de uma venda de teste. Em todos os casos decide a política do vendor: com `CONTINUE`, o pedido é criado sem
número.

**Se você já numerou.** Um caixa que numerou com `POST /fiscal/numbering` e depois injeta com o mesmo
`orderCode` não é numerado duas vezes: o Fire reaproveita esse documento e responde `CONTINUE`.

**Duplicados.** A numeração fica atrelada ao `orderId`. O mesmo `orderId` com outro `orderCode` não é
numerado de novo: se o pedido existe, você recebe o `409` de sempre; se não existe, é uma falha de
numeração (`FISCAL_IDEMPOTENCY_CONFLICT`) que a política resolve.

## Erros

Todo erro traz `success: false`, `error` (a categoria) e `message`; alguns trazem `code`, `data` ou
`details`. Este endpoint **não responde `422`**: as rejeições de negócio são `400`
`BUSINESS_ERROR`.

| HTTP | `error` / `code` | Quando |
|---|---|---|
| `400` | `VALIDATION_ERROR` | Falta `orderCode` ou ele vem vazio; também com corpo vazio ou JSON inválido. `message`: `orderCode is required and must be a non-empty string` |
| `400` | `VALIDATION_ERROR` | O corpo não tem o formato. `details` lista cada problema com o seu `path` |
| `401` | `UNAUTHORIZED` | Falta a API key, ela não começa com `pk_live_`, ou está vencida ou revogada |
| `403` | `FORBIDDEN` | API key sem escopo `orders:write`, ou não associada a uma conta |
| `404` | `NOT_FOUND` | Não há loja com esse `store.code` + `store.vendorId`. `message`: `Store not found with ID <code>` |
| `400` | `BUSINESS_ERROR` | Loja inativa ou não publicada. `message`: `Store <code> is not active or not published. …` |
| `400` | `BUSINESS_ERROR` | Dia de negócio fechado. `message`: `Store <code> business day is not open. …` |
| `400` | `BUSINESS_ERROR` + `details.code: ORDER_INVARIANT_VIOLATION` | O pedido não cumpre uma regra de validação ativada para o seu vendor. Ver abaixo |
| `409` | `CONFLICT` / `DUPLICATE_ORDER` | O pedido já existia para esse vendor. Ver [Duplicados](#duplicados) |
| `400` | `DOMAIN_ERROR` ou `BUSINESS_ERROR` com `message` que começa com `Failed to` | Falha interna do Fire, não do seu pedido |
| `503` | `SERVICE_UNAVAILABLE` | Não foi possível verificar a API key naquele momento |
| `500` | `INTERNAL_SERVER_ERROR` | Erro inesperado |
| `400` | `BUSINESS_ERROR` + `details.code: FISCAL_NUMBERING_FAILED` | Só com numeração na injeção: a numeração falhou e a política do vendor é `REFUND`. `details.fiscal` traz o bloco. O pedido não foi criado |

### Rejeição por regras de validação

Cada vendor pode ativar, por canal, regras que revisam o pedido antes de guardá-lo. Um pedido que
passa na validação do formato pode ainda assim ser rejeitado aqui. A rejeição não acrescenta
chaves na raiz: tudo o que é novo vai em `details`.

| `details.violations[].category` | O que aconteceu |
|---|---|
| `TAX_MISSING` | Um produto ou modificador com preço não traz impostos |
| `TAX_MALFORMED` | Impostos incompletos (sem `name`, `rate`, `amount` ou `base`), que não somam o total de impostos, ou o mesmo imposto escrito de duas formas |
| `ORDER_NOT_BALANCED` | Os produtos não somam o total do pedido |
| `PRODUCT_NOT_MAPPED` | Um produto sem `additionalInfo.externalCode` |
| `CASH_CHANGE_INVALID` | Um pagamento em dinheiro com troco incoerente |
| `PRODUCT_TYPE_MISMATCH` | Um produto ou modificador enviado com um `type` diferente do menu sincronizado, ou sem `type`. Com a regra ativada, um sem `type` é sempre rejeitado, esteja ou não no catálogo. `expected` é o tipo do menu, ou `null` se você não enviou `type` e o tipo resultante é `PRODUCT` (menu `PRODUCT` ou produto fora do catálogo); `received`, o que você enviou, ou `""` se não enviou nenhum |

Cada violação traz `invariant`, `category` (estável, para automatizar), `path` (o caminho dentro do
corpo que você enviou, como `order.products[0]`), `expected` e `received` (decimais nas regras de valores; nomes de tipo em `PRODUCT_TYPE_MISMATCH`, onde `expected` pode ser `null`), e `message`.
Em `ORDER_NOT_BALANCED`, `lines` diz quanto soma cada produto.

<Note>
  Passar na validação do formato não garante que o pedido seja aceito. O exemplo desta página não
  traz `taxes[]` por produto: com a regra de impostos ativada para o seu vendor, seria rejeitado com
  `TAX_MISSING`.
</Note>

```json
{
  "success": false,
  "error": "BUSINESS_ERROR",
  "message": "Order rejected — 1 problem. [I6] order.products: the products add up to 73.70 but the order total is 75.70 (difference 2.00). A product, an option or a price is missing.",
  "details": {
    "code": "ORDER_INVARIANT_VIOLATION",
    "orderCode": "AGG-KEETA-K066-…",
    "externalOrderId": "…",
    "violations": [
      { "invariant": "I6", "category": "ORDER_NOT_BALANCED", "path": "order.products", "expected": "75.70", "received": "73.70",
        "message": "…", "lines": [{ "path": "order.products[0]", "externalCode": "30033", "name": "…", "total": "73.70" }] }
    ]
  }
}
```

### Recusa pela numeração fiscal

Só com [numeração na injeção](#numeração-fiscal-na-injeção) e a política `REFUND`. O mesmo envelope
das regras de validação: tudo vai em `details`.

```json
{
  "success": false,
  "error": "BUSINESS_ERROR",
  "message": "Could not number the sale",
  "details": {
    "code": "FISCAL_NUMBERING_FAILED",
    "orderCode": "…",
    "externalOrderId": "…",
    "fiscal": {
      "action": "REFUND",
      "requestStatus": "FAILED_RETRYABLE",
      "failure": { "code": "PROVIDER_UNAVAILABLE", "message": "…" }
    }
  }
}
```

### Quando tentar de novo

| Resposta | O que fazer |
|---|---|
| `201` | Nada. |
| `409` `DUPLICATE_ORDER` | **Não tentar de novo**: o pedido já está lá. Usar `data.id`. |
| `400` com `details.code: FISCAL_NUMBERING_FAILED` | **Não reenviar**: devolver o dinheiro e informar a [venda perdida](/pt/api-reference/lost-sales#se-o-seu-vendor-numera-na-injeção) com `reason: "FISCAL_NUMBERING_FAILED"` e `details.fiscal.failure` em `detail`. |
| `400` `VALIDATION_ERROR`, `400` com `ORDER_INVARIANT_VIOLATION`, `401`, `403`, `404` | Corrigir e reenviar com o mesmo `orderId`. Uma nova tentativa idêntica falha igual. |
| `400` `BUSINESS_ERROR` por loja inativa ou dia fechado | Tentar de novo quando o estado mudar. Depois de abrir o dia, a loja pode levar até 30 segundos para aceitar pedidos. |
| `400` com `message` que começa com `Failed to`, `503`, `500` | Tentar de novo com backoff. É seguro: se o pedido já tinha entrado, a resposta é `409`. |

<Info>
  Toda requisição autenticada fica registrada no Fire com o seu corpo e o seu resultado, inclusive
  as rejeitadas.
</Info>
