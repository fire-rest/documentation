Your system injects orders into Fire through the REST API. Fire validates the order, stores it in
the store's open business day, fills in what is missing (in Brazil, the taxes) and notifies you of
status changes with [events](/en/events/overview).

<Note>
  Injection is the same with or without the fiscal gateway. With the gateway, the till requests the numbers before injecting. See [How fiscal works in Fire](/en/fiscal/overview).
</Note>

## Which endpoint to use

There are four entry points and all of them end in the same core: same validations, same business
day, same events. Choose by the format your system already builds.

| Your system | Endpoint | Reference |
|---|---|---|
| Partner that sends orders in Fire format and resolves the store by `store.code` + `store.vendorId` (X-MART Gateway, kiosks and tills in Brazil) | `POST /api/v1/adapters/xmart/stores/orders` | [Inject order (partners)](/en/api-reference/inject-order-partners) |
| Your own system sending orders in Fire format with its API key | `POST /api/v1/external/orders` | [Create order (v1)](/en/api-reference/create-order) |
| Till, kiosk or integrator sending the POS and kiosk structure or the aggregator structure | `POST /api/v2/external/orders` | [Create order (v2)](/en/api-reference/create-order-v2) |
| Aggregator (iFood, Rappi, Keeta…) through the aggregator integration | `POST /api/v4/integrations/sales/aggregator/orders` | [Inject order](/en/api-reference/orders) |

The rest of this guide uses the partners endpoint as the example; the rules apply to all of them.

## Flow

1. Your system charges, or leaves the payment pending, and builds the order with store, channel,
   service, products and payments.
2. You send the order to the endpoint with your API key in the `x-api-key` header.
3. Fire looks up the store, checks that it is active and has an open business day, resolves channel
   and service, and runs the validation rules enabled for your vendor.
4. In Brazil, Fire calculates the taxes of every line with the store's fiscal group and the
   catalog's NCM.
5. Fire stores the order and responds `201` with `data.id`. Keep it: it is the id you later use to
   read the order, [confirm the payment](/en/api-reference/confirm-payment) or
   [cancel it](/en/api-reference/cancel-order-partners).
6. Fire emits [`order.completed`](/en/events/order-completed) if every payment came `APPROVED`,
   or [`order.opened`](/en/events/order-opened) if the order was born open. Later changes arrive
   as events: see [Order status notifications](/en/guides/order-status).

## What fails most often in a certification

Five points account for almost every rejection and unbalanced order. Check them before sending the
first order.

1. **Store and vendor.** Fire looks up the store by `store.code` + `store.vendorId`. `store.id`
   is stored as a reference but not used for the lookup: make it point to the same store as
   `store.code`. An inactive store, or one with a closed business day, rejects the order with
   `400`.
2. **Channel and service.** `channel.code` and `service.code` must match the ones configured for
   your vendor, spelled the same way (`KIOSK`, not `Kiosk`). A code Fire does not recognize does
   not reject the order, but leaves it without a channel and without its payment and printing
   policy.
3. **Modifiers with quantity.** If the parent product carries `quantity: 2`, every modifier
   carries `quantity: 2` and `totalPrice.total = unitPrice.total × 2`. The sum of
   `totalPrice.total` across products and modifiers is the order total; if it does not add up,
   `ORDER_NOT_BALANCED`.
4. **Sum of payments.** The sum of `paymentMethods[].totalBill` equals
   `payments.totals[0].total`. Discounts go in `payments.discounts[]` and the total already
   reflects them.
5. **Taxes in Brazil.** Do not send them: Fire calculates them with the store's fiscal group and
   the catalog's NCM. Before the first order, confirm that the store belongs to a fiscal group and
   that every product has a fiscal category. If you send `taxes[]` or `payments.metadata.fiscal`,
   Fire keeps your taxes and calculates nothing.

Each point is developed, with examples, in
[Inject order (partners)](/en/api-reference/inject-order-partners).

## Duplicates and retries

The duplicate key is `orderId` + `store.vendorId`. Resending an order that already went in
responds `409` `DUPLICATE_ORDER` with the existing order's `id`: treat it as ingested, not as an
error.

<Warning>
  A validation `400` is fixed and resent with the same `orderId`; an identical retry fails the same
  way. A `500`, a `503` or a `400` whose `message` starts with `Failed to` is retried with
  backoff: if the order had already gone in, the response is `409`.
</Warning>
