The **Single order** tab lets you build a single order from the store's **real menu** — the same catalog the POS reads — and inject it directly into FIRE. Use it to reproduce a specific case end to end: pick real products and modifiers, choose the channel and service, set payment and client data, and (for Brazil) let FUEL enrich the fiscal document so FIRE emits the NFC-e.

![Single order tab — POS-style menu with context sidebar and results log](/images/fuel/tab-single-order-en.png)

<Note>
  You must select a full operating context (environment, account, country, vendor, and store) in the sidebar before the tab becomes functional. The menu is queried live from the selected store.
</Note>

<Note>
  Single order no longer uses "test menus". It reads the **real catalog** from the store via `productsBy`, so the environment must have a catalog host (`xmart_url`) configured. For Brazil, fiscal enrichment also requires a fiscal engine host (`fiscal_engine_url`). See [Setup](/en/fuel/setup#environments).
</Note>

## How it works

The flow mirrors a POS sale end to end:

```
real menu (productsBy) → cart → build order → (Brazil: fiscal enrichment) → inject to FIRE
```

FUEL builds the POS-style payload and maps it to the format FIRE accepts directly. For Brazil, before injecting it calls the fiscal engine (`/enrich-order`), which returns the order with the correct per-line taxes, so FIRE can issue the fiscal receipt instead of getting stuck "processing".

## Building and injecting an order

<Steps>
  <Step title="Choose channel and service">
    Channel and **Service / delivery** are independent axes, shown at the top of the tab.

    - **Channel** — grouped into **Main** (`POS`, `KIOSK`, `APP`), **Aggregators** (iFood, Rappi, Uber, …), and **Other**. The core channels are always available even if the store doesn't list them. Each option shows an icon.
    - **Service / delivery** — `DINE_IN`, `TAKEAWAY`, `DELIVERY`, `PICKUP`, or `DRIVE_THRU`. This is the axis that scopes the menu.

    The catalog view adapts to the channel: a full-width **POS** frame, a vertical **KIOSK** frame, a phone-style **APP** frame, or a medium remote frame for aggregators.
  </Step>

  <Step title="Browse the real menu">
    The tab loads the store's live catalog (categories + products) for the selected service. Products are shown as cards with their image and price, exactly as the POS presents them. Combos show a **REF** (reference) price and a **COMBO** badge.

    Switch categories with the tabs above the grid. Unavailable products are greyed out.
  </Step>

  <Step title="Add products with modifiers and notes">
    Tap a product to open its panel. There you can:

    - Select **modifier groups** — required groups must have a valid selection before you can add the item; optional groups can be left empty. Modifier prices are shown per option (a `DEFAULT` badge marks preselected options).
    - Set the **quantity**.
    - Add an optional **note for the product** (`productComment`) — kitchen instructions such as "no salt".

    Tap **Add**. The item goes to the cart bar at the bottom, which stays visible while you keep browsing.
  </Step>

  <Step title="Open the order builder">
    From the cart bar you can adjust quantities or remove lines. When ready, click **Build order** to open the checkout dialog.
  </Step>

  <Step title="Review the order preview">
    The dialog opens with an **order preview**: each line shows the product image, quantity, selected modifiers, and price. You can still edit the **note per product** here.
  </Step>

  <Step title="Set payment and transaction status">
    In the **Payment** section:

    - **Processor** — pick the payment method available for the country (cash, card, PIX, Mercado Pago, …). Each option shows an icon and a readable label next to its code.
    - **Transaction status** — `APPROVED`, `PENDING`, or `REJECTED`. This drives how FIRE resolves the order and payment state.
  </Step>

  <Step title="Fill in client / fiscal data (optional)">
    Toggle **Client / fiscal** on to send customer data. Fields are driven by the country:

    - **Document type** and **number** (per-country picker; e.g. CPF/CNPJ for Brazil, RUC for Ecuador). "Final consumer" is the anonymous default.
    - **First name**, **last name**, **email**, **phone**.

    Left off, the order is sent as an anonymous final consumer.
  </Step>

  <Step title="Add delivery address and comment (when applicable)">
    - When the service is **DELIVERY**, a **delivery address** form appears (street, number, city, ZIP/postal code, reference, contact phone).
    - The **Issue fiscal receipt** toggle (`invoice_print`) controls whether FIRE emits the fiscal document. It is on by default — leave it on for fiscal tests.
    - Add an optional **order comment** for the whole order.
  </Step>

  <Step title="Inject to FIRE">
    Click **Inject to FIRE**.

    - For **Brazil**, the button first **enriches** the order via the fiscal engine (you'll see *Enriching fiscal…* then *Injecting…*), and injects the enriched payload. If enrichment fails (for example `FISCAL_MATRIZ_SIN_NCM`), the error is shown and nothing is injected.
    - For other countries, the order is injected directly.

    The **injected payload** (enriched, for Brazil) is available in the dialog with **View**, **Copy JSON**, and **Download**. The result banner shows the **external ID**, **FIRE UID** (when returned), **status**, and **payment** status, and the injection is recorded in the shared results log on the right.

    A new `orderId`/`orderCode` is generated for the next injection to avoid idempotency (409) rejections.
  </Step>
</Steps>

## Combos and fiscal

Fixed-price combos are injected as a **single line carrying the full price on the parent**, with the components kept as detail. This matches how the POS itemizes combos and lets the fiscal engine tax the parent by its NCM, so combos emit a fiscal receipt end to end.

<Note>
  If a combo's components are not loaded in the fiscal engine's price matrix (`matriz_precos`) for the store, the fiscal engine can still tax the single parent line — but full per-component itemization requires that data to be loaded on the fiscal side.
</Note>
