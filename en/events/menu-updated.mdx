<Note>
  **Limited availability.** This event is being rolled out and is enabled per account. Ask your Fire contact whether it already applies to yours.
</Note>

<Warning>
  This is the **Integration Flows** `menu.updated` event, documented on this page. It is **not** the aggregator-integration webhook with the same name described in [Webhook reference → `menu.updated`](/en/webhook-reference/menu-updated): that is the format of existing integrations, has a different shape, and does not change.
</Warning>

`menu.updated` fires every time a store's menu is **synchronized** for a channel and a fulfillment type. It always carries the **whole menu** of that combination — never a diff. Treat it as a full replacement of the menu you have for it.

We call that combination a **terna**: **store × channel × fulfillment type** (for example, Laboratorio · `KIOSK` · `TAKEAWAY`). Each terna has a fixed id, `data.menuSyncId`, which also travels in [`product.updated`](/en/events/product-updated) and links the two events.

## Trigger condition

- **Synchronizing the menu** of one or more ternas (for example, from Menu assignments) emits **one** `menu.updated` **per terna**.
- **Saving a price change** in the prices and availability editor emits the `menu.updated` of the edited terna, besides the price [`product.updated`](/en/events/product-updated). The other ternas sharing that menu get the change in their next synchronization.
- **Removing the assignment** of a terna's menu or price list emits a **withdrawal** `menu.updated`: the last menu that terna received, with `menu.menus[0].status: "INACTIVE"`. See [Withdrawal](#withdrawal).

Every event produced by the same action shares `data.groupId`.

**Nothing is emitted** when the catalog is edited without synchronizing, or when a product is turned off or back on: that is a [`product.updated`](/en/events/product-updated). A flow limited to some channels receives only the ternas of those channels.

| | |
|---|---|
| Coverage | All countries, on accounts where the event is enabled |
| Unit | One terna: `data.store` × `data.channel` × `data.fulfillment` |
| Terna id | `data.menuSyncId` — fixed; it is also `data.menu.menus[0].id` |
| Action id | `data.groupId` — the same in every event of that action |
| Delivery id | `event.id`, as in every event (the flow execution) |
| Entity | `_meta.triggerEntityId` is `data.menuSyncId` |

## General rules

1. **One product model.** Every product in `data.menu.products[]` uses the same fields as a product in [`product.updated`](/en/events/product-updated). Names are camelCase (`modifierGroups`, `outOfStockUntil`).
2. **Texts per language.** Every visible text is `{ "<locale>": "text" }`, in the language of the store's country (`es-EC`, `pt-BR`, …).
3. **Prices.** `price` is what is charged (offer included). `anchorPrice` is the struck-through list price and only appears when there is an offer.
4. **Schedules in the store's local time** (`store.locationInfo.timezone`). See [Schedules](#schedules).
5. **`metadata` only carries catalog data.** Whatever is not here does not travel in the event.

### The product as an option

The same product can be an option in several groups and cost differently in each: the drink is worth `0` inside the combo and `1.00` as an add-on. Each entry in `pricing.modifiers[]` says how it is sold **in that group**:

| Field | What it is |
|---|---|
| `modifierGroupId` | The group (`modifierGroups[].id`). |
| `price` | What is charged when chosen in that group, offer included. |
| `anchorPrice` / `anchorPricePercentage` | List price and discount; only when the option has an offer. |
| `isTaxInclusive`, `taxRate` | Same as in the product. |
| `minimumQuantity` / `maximumQuantity` | How many units of **this option** can be chosen. |
| `defaultQuantity` | Preselected quantity. |
| `displayType` | How it is chosen: `RADIO` (only one of the group), `CHECKBOX` (check or not) or `QUANTITY` (quantity selector). |

### `menu.categories[]`

| Field | What it is |
|---|---|
| `id`, `name`, `imageUrl` | Category identity. `description` is always `null`. |
| `items[]` | The category's products **in display order**: `{ "type": "PRODUCT", "id": "…" }`. |
| `availability.status` | `ACTIVE` (shown) or `HIDDEN` (exists but is not shown). |
| `availability.schedules` | The category's own schedule, or `null`. `inactiveUntil` is always `null`. |
| `metadata` | Always `{}`. |

The **category order** is the one in `menus[0].categoryIds`.

### `menu.modifierGroups[]`

| Field | What it is |
|---|---|
| `id` | Group id (see the note). |
| `title` | Displayed title. `description` is always `null`. |
| `displayType` | Always `"LIST"`. How each option is chosen goes in `pricing.modifiers[].displayType`. |
| `modifierIds[]` | Products that are options in this group, in display order. They point to `products[].id`. |
| `minimumQuantity` | Minimum to choose (`1` or more = required). |
| `maximumQuantity` | Maximum to choose. **`9999` = no limit.** |
| `chargeAboveQuantity` | Always `null`. `metadata` is always `{}`. |

<Note>
  **A catalog group can arrive as several copies.** `{id}` is the group as is; `{id}-{hash}` is a copy for when different parent products put **different prices** on the same options, and `{id}-x{hash}` breaks a **cycle** (a product that, through its options, would reach itself). For you they are regular groups: follow the parent's `pricing.modifierGroupIds`. The ids are stable as long as the prices that produce them do not change, and the next menu always carries the current ones.
</Note>

### `menu.recommendations[]`

| Field | What it is |
|---|---|
| `id` | `rec-{hash}`. |
| `title` | Displayed name (the suggested product's). `description` is always `null`. |
| `type` | `UPSELL` (switch to something bigger) or `CROSS_SELL` (add something else). |
| `targetProductId` | The suggested product (`products[].id`). |
| `metadata` | Always `{}`. |

### `menu.menus[0]` — the header

| Field | What it is |
|---|---|
| `id` | Equal to `menuSyncId`. |
| `name` | Menu name in the catalog. `description` is always `null`. |
| `schedules` | The terna's **effective** sales schedule, already resolved (store → channel → fulfillment type). `null` = 24/7. |
| `categoryIds[]` | The categories, in display order. |
| `status` | `ACTIVE` on a synchronization; `INACTIVE` on a [withdrawal](#withdrawal). |
| `metadata.catalogMenuId` | Id of the catalog menu assigned to the terna. Several ternas can share a menu. |
| `metadata.store` | A copy of `store.metadata`, for whoever reads the stored menu without the event at hand. `{}` when the store has no data. |

## Schedules

The format is the same in the menu, the category and the product:

```json
[
  { "dayOfWeek": "monday", "periods": [{ "startTime": "09:00:00", "endTime": "22:30:00" }] },
  { "dayOfWeek": "sunday", "periods": [] }
]
```

- **All 7 days** always come, from `monday` to `sunday`, in lowercase.
- Store local time, `HH:MM:SS` format. `periods: []` = closed that day.
- A schedule that crosses midnight comes **split** into two days (Friday `22:00:00–23:59:59` and Saturday `00:00:00–02:00:00`). A close at `00:00` comes as `23:59:59`.
- `null` instead of the list = no restriction.

## Withdrawal

When a terna's menu or price list is unassigned, the terna is left with no menu to sell. Fire announces it with a withdrawal `menu.updated`:

- It carries the **last menu that terna received**, unchanged, with `menu.menus[0].status: "INACTIVE"`.
- It has its own `data.groupId`, so deduplication does not mistake it for the previous menu.
- It is sent only if the terna had already received a menu with products. A terna that never received a menu gets no withdrawal.

**What to do:** stop showing and selling that menu on that terna. If a menu is assigned to it again later, the next `menu.updated` arrives with `status: "ACTIVE"` and replaces it as usual.

## Delivery and order

- **The menu wins.** Each `menu.updated` carries the terna's complete state: the latest one replaces everything before it. Between one menu and the next, [`product.updated`](/en/events/product-updated) applies quick changes.
- **In order per terna.** Within a flow, the `menu.updated` events of **the same terna** are delivered one at a time, in the order they were emitted; different ternas move in parallel. A `menu.updated` and a `product.updated` have no guaranteed order between them: order by `event.emittedAt`.
- **Deduplicate by `data.groupId` + `data.menuSyncId`.** `event.id` identifies the delivery, not the fact (see [Idempotency on your side](/en/events/delivery#idempotency-on-your-side)).
- **Respond fast.** Return `2xx` as soon as you receive it and process afterwards: a full menu is large, and a timeout causes retries.
- **If your system processes asynchronously**, you can report the final result with the [menu result callback](/en/api-reference/catalog-menu-result).

## Example handler

```js
async function onMenuUpdated(event, data) {
  const key = `${data.groupId}:${data.menuSyncId}`;
  if (await db.appliedMenus.exists(key)) return; // already applied

  // Withdrawal — the terna has no menu on sale anymore
  if (data.menu.menus[0].status === "INACTIVE") {
    await db.menus.deactivate(data.menuSyncId, { emittedAt: event.emittedAt });
    await db.appliedMenus.add(key);
    return;
  }

  // Full replacement — the event carries the terna's whole menu
  await db.menus.replace(data.menuSyncId, {
    store: data.store.uid,
    channel: data.channel.code,
    fulfillment: data.fulfillment.service.code,
    emittedAt: event.emittedAt,
    menu: data.menu,
  });
  await db.appliedMenus.add(key);
}
```

## Common mistakes

- **It is not a diff.** A product missing from the event is no longer in that terna's menu. Replace, do not merge.
- **Do not show `optionOnly` products.** They exist only as an option of a group.
- **Out-of-stock travels in the product.** `availability.status: "OUT_OF_STOCK"` with its `outOfStockUntil`: there is no separate list.
- **Group copy ids can change** if the prices that produce them change. Always take the ones from the latest menu.
- **A withdrawal arrives as `menu.updated`.** There is no "menu deleted" event: check `menu.menus[0].status`. With `INACTIVE` the terna has no menu on sale anymore (see [Withdrawal](#withdrawal)).
