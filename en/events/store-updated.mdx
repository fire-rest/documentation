title: "store.updated"
description: "A store's configuration was published to its channels — the whole store, its channels with resolved schedules, and the publication that produced the event."
---

<Note>
  **Limited availability.** This event is being rolled out and is enabled per account. Ask your Fire contact whether it already applies to yours.
</Note>

<Warning>
  This is the **Integration Flows** `store.updated` event, documented on this page. It is **not** the aggregator-integration webhook with the same name described in [Webhook reference → `store.updated`](/en/webhook-reference/store-updated): that one belongs to a different system, has a different shape, and does not change.
</Warning>

`store.updated` fires every time a store's configuration is **published** to its channels: first publication, publishing a draft, re-synchronizing, switching a channel on or off, applying an override, archiving. It always carries the **whole store** — never a diff. Treat it as a full replacement of what you know about that store.

Like `store.business_day_closed`, it is a **store-level** event: one per publication, not one per order or per channel. A publication that touches several channels produces a single event with every channel inside, and each flow that receives it gets that event once, with the whole store.

## Trigger condition

Each publication of a store emits **one** `store.updated`. `data.publication.reason` tells you what produced it:

| `reason` | What happened |
|---|---|
| `publish` | The store was published for the first time (also when a store is created already published). |
| `draft` | The pending changes of a published store were applied. Channels being switched off travel with `enabled: false`. |
| `resync` | Someone re-synchronized the store; it travels exactly as it is. |
| `channel_toggle` | A channel was switched on or off for the store, by hand or by its schedule. |
| `override_apply` / `override_revert` | An override was applied to the store, or reverted. |
| `archive` | The store was archived — see [Archiving](#archiving). |

New `reason` values (the contract already allows `retry`) and new `mode` values may appear. Treat a value you do not know as a normal publication: the event still carries the whole store.

A publication can also be **scheduled**: nothing is emitted when it is scheduled; the event fires when the scheduled time arrives, with `publication.mode: "scheduled"` and `publication.scheduledAt`. Cancelling a scheduled publication emits nothing.

**Nothing is emitted** when changes are saved without publishing them to the channels, or when the business day opens or closes.

| | |
|---|---|
| Coverage | Every country, on accounts where the event is enabled |
| Publication id | `data.publication.id` — the same in every delivery and in every flow that receives that publication |
| Delivery id | `event.id`, as in every event (the flow execution) |
| Order | `data.publication.sequence`, per store — see [The latest publication wins](#the-latest-publication-wins) |
| Entity | `_meta.triggerEntityId` is the store UUID (`data.store.uid`) |

<Note>
  A flow limited to certain channels receives a publication when it touches **at least one** of them — and it receives the **whole** event, every channel included. Pick the channels that are yours from `data.channels`.
</Note>

## `data.*` reference

### `data.store`

<ResponseField name="store" type="object">
  The **same V4 store block** that travels on order events — `uid`, `code`, `name`, `phone`, `email`, `address`, `externalId`, `vendor`, `account`, `locationInfo` (with `country.phoneCode`), `metadata` and `storeFiscalConfig` (may be `null`). Field reference in [`order.completed` → `data.store`](/en/events/order-completed#data-store). `phone` comes in international format (`+` and digits, e.g. `+5511999990000`). It may carry a number that is not real (for example, all zeros) if the store has no phone set, or the value exactly as stored if the country has no calling code. `metadata` is the store's **free key-value** configuration: Fire does not impose its keys, some integrations read well-known ones (in the example, `taxesInfo` and `deliveryInfo`), and it is `{}` when the store has none. On top of that block, this event adds:

  <Expandable title="fields added by store.updated">
    <ResponseField name="number" type="integer | null">
      The store's sequential number in Fire. `null` when it is not known.
    </ResponseField>
    <ResponseField name="status" type="string">
      Publication state of the store: `DRAFT`, `PUBLISHED`, `PARTIALLY_PUBLISHED` or `ARCHIVED`.
    </ResponseField>
    <ResponseField name="active" type="boolean">
      Whether the store is active. Always `false` when archived.
    </ResponseField>
  </Expandable>
</ResponseField>

### `data.channels`

<ResponseField name="channels" type="array">
  **Every** channel configured for the store — not only the ones this publication is about (those are in `publication.channels`). A channel or fulfillment type that is switched off still travels, with `enabled: false`: that is how you learn it was taken down.

  <Expandable title="channels[]">
    <ResponseField name="code" type="string">
      Channel code, written as configured in Fire (`KIOSK`, `POS`, `iFood`, `99`, …). Compare without assuming a particular case.
    </ResponseField>
    <ResponseField name="enabled" type="boolean">
      Whether the channel is enabled for the store.
    </ResponseField>
    <ResponseField name="published" type="boolean">
      Whether the channel is among the store's published channels.
    </ResponseField>
    <ResponseField name="fulfillmentTypes" type="array">
      The channel's fulfillment types.
      <Expandable title="fulfillmentTypes[]">
        <ResponseField name="code" type="string">Fulfillment type code (`DELIVERY`, `TAKEAWAY`, `DINE_IN`, …).</ResponseField>
        <ResponseField name="enabled" type="boolean">Whether the fulfillment type is enabled on this channel.</ResponseField>
        <ResponseField name="schedules" type="array">
          The **effective** schedule, already resolved: the fulfillment type's own schedule; if it has none, the channel's; if the channel has none either, the store's `salesSchedule`. Each entry is `{ day, startTime, endTime }`, same shape as below. You do not need to apply the inheritance yourself.
        </ResponseField>
      </Expandable>
    </ResponseField>
  </Expandable>
</ResponseField>

### `data.operationSchedule` and `data.salesSchedule`

<ResponseField name="operationSchedule" type="array">
  The store's operating hours. Each entry: `day` (`MONDAY` … `SUNDAY`), `startTime` and `endTime` (`HH:mm`).
</ResponseField>
<ResponseField name="salesSchedule" type="array">
  The store's sales hours, same shape. It is the fallback for channels and fulfillment types without a schedule of their own — already applied in `channels[].fulfillmentTypes[].schedules`.
</ResponseField>

### `data.salesGoals`

<ResponseField name="salesGoals" type="object">
  The store's sales goals: the goal for the **current month and future months**, already split by day. Amounts are **net sales, excluding taxes**, in the store's currency. Only present when the store has goals set; otherwise the field is omitted. Only sent in `store.updated`, never in any other event.

  <Expandable title="salesGoals">
    <ResponseField name="version" type="integer">Shape version. Currently `2`.</ResponseField>
    <ResponseField name="currency" type="string">Currency of the amounts (ISO 4217, e.g. `BRL`).</ResponseField>
    <ResponseField name="months" type="array">
      One item per month with a goal, in order.

      <Expandable title="months[]">
        <ResponseField name="month" type="string">Month, `YYYY-MM`.</ResponseField>
        <ResponseField name="amount" type="number">Month goal. Equals the sum of `days[].amount`.</ResponseField>
        <ResponseField name="distribution" type="string">How it was split by day: `HISTORY` (by how much the store sells on each weekday) or `EVEN`.</ResponseField>
        <ResponseField name="weights" type="number[]">Optional. The 7 weights used, Monday to Sunday.</ResponseField>
        <ResponseField name="days" type="array">Every day of the month: `date` (`YYYY-MM-DD`), `amount` (day goal, 2 decimals) and `fixed` (`true` if set by hand; `amount: 0` with `fixed: true` = closed day).</ResponseField>
        <ResponseField name="updatedAt" type="string">When that month's goal was changed (ISO 8601, UTC).</ResponseField>
        <ResponseField name="updatedBy" type="object">Who changed it: `{ id, name }`.</ResponseField>
      </Expandable>
    </ResponseField>
  </Expandable>
</ResponseField>

A week's goal is the sum of its days. Hourly goals are not sent: if you need them, split the day goal using your own hourly profile.

### `data.publication`

<ResponseField name="publication" type="object">
  The publication that produced this event.

  <Expandable title="publication">
    <ResponseField name="id" type="string">
      UUID of the publication. The same in every delivery and in every flow that receives it — use it to recognize a publication you already applied.
    </ResponseField>
    <ResponseField name="sequence" type="integer">
      Per-store counter: it goes up by one with each emitted publication of that store. The higher one is the newer one. See [The latest publication wins](#the-latest-publication-wins).
    </ResponseField>
    <ResponseField name="mode" type="string">
      `now` (published on the spot) or `scheduled` (fired by a schedule). New values may appear; treat them as a normal publication.
    </ResponseField>
    <ResponseField name="reason" type="string">
      What produced the publication: `publish`, `draft`, `resync`, `channel_toggle`, `override_apply`, `override_revert` or `archive`. New values may appear (e.g. `retry`); treat them as a normal publication. See [Trigger condition](#trigger-condition).
    </ResponseField>
    <ResponseField name="channels" type="string[]">
      The channel codes this publication is about: the ones chosen when publishing, every enabled channel on a re-sync, the channel switched on or off in a `channel_toggle`, the single channel of a one-channel re-sync, every enabled channel on an `override_apply` or `override_revert`, and on archiving, the published channels plus the enabled ones.
    </ResponseField>
    <ResponseField name="scheduledAt" type="string | null">
      ISO 8601 UTC time the publication was scheduled for. `null` when `mode` is `now`.
    </ResponseField>
    <ResponseField name="requestedBy" type="object">
      `{ id, name }` — who requested it. Either can be `null`; automatic runs may arrive with `id: null` and `name: "CRON"`.
    </ResponseField>
  </Expandable>
</ResponseField>

## The latest publication wins

Every event carries the **whole** store, so the most recent publication replaces everything before it. Fire already takes care of the order for you:

- Within a flow, the publications of **one store** are delivered one at a time, in the order they were emitted. Different stores move in parallel.
- When a store gets a new publication that covers the same channels, deliveries of older publications that were still waiting are cancelled; the others still go out, in order.

`publication.sequence` is still useful data: you can store the last one you applied per store, and recognize a stale payload if one ever reaches you — for example, a manual replay of an old delivery, which keeps its original `sequence`.

## Archiving

Archiving a store emits a `store.updated` with `publication.reason: "archive"`. It carries the archived store: `store.status: "ARCHIVED"`, `store.active: false`, and **every** channel and fulfillment type with `enabled: false` (and channels with `published: false`). To handle archiving separately, branch on `reason` or on `status`.

<Note>
  Integration Flows do not emit a separate `store.deleted` event: archiving is a `store.updated`.
</Note>

## Handler example

```js
async function onStoreUpdated(data) {
  const { store, channels, publication } = data;

  // 1. Already applied this publication? (same id on every delivery)
  if (await db.storePublications.exists(publication.id)) return;

  // 2. Optional: keep the sequence to recognize a stale payload
  const last = await db.stores.lastSequence(store.uid);
  if (last != null && publication.sequence < last) return;

  // 3. Full replacement — the event carries the whole store
  const mine = channels.filter((c) => MY_CHANNELS.includes(c.code.toUpperCase()));
  await db.stores.replace(store.uid, {
    code: store.code,
    name: store.name,
    active: store.active,
    archived: store.status === "ARCHIVED",
    metadata: store.metadata,
    channels: mine,
    sequence: publication.sequence,
  });
  await db.storePublications.add(publication.id);
}
```

## Common pitfalls

- **It is not a diff.** A channel missing from your copy is not "unchanged" — the event lists every channel. Replace, do not merge.
- **A switched-off channel still travels.** Read `enabled`; do not assume that a channel present in the event is open.
- **`publication.channels` is not the list of channels.** It says what this publication was about; the store's channels are in `data.channels`.
- **Do not dedupe by `event.id`.** It identifies the delivery; the publication is `data.publication.id`.
- **Channel codes keep the case they were configured with** (`iFood`, `KIOSK`). Normalize before comparing.
