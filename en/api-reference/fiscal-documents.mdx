---
title: "Request fiscal numbering"
api: "POST /api/v1/external/fiscal/numbering"
description: "Gets the fiscal identifiers the point of sale needs to print the receipt. It is synchronous: you call it after charging and before injecting the order."
authMethod: "key"
---

Fire resolves internally which fiscal provider matches the store's country, asks it for the
numbering, and returns the data ready to print.

<Info>
  **Three things before you integrate:**

  1. **There is no order id here.** At charge time the order does not exist in Fire yet. The
     `orderCode` is the only thing tying this request to the sale, so it must be **the same
     string** you later send when injecting the order.
  2. **The response does not mean the document is authorized.** It means there are numbers to
     print. The tax authority's approval arrives later, asynchronously.
  3. **You request an operation, not a document type.** `INVOICE` or `CANCEL`. Which fiscal
     instrument materializes it — invoice, credit note, cancellation event — is decided by
     the country, and is not the point of sale's concern.
</Info>

## The full flow

<Steps>
  <Step title="You charge">
    The customer pays at the POS or kiosk.
  </Step>
  <Step title="You request the numbering">
    You call this endpoint. Fire resolves the store, the issuer and the provider, and stores
    the request **before** going out for the numbers.
  </Step>
  <Step title="You print">
    Based on `printing.mode` you print the fiscal receipt or a provisional ticket.
  </Step>
  <Step title="You inject the order">
    With your usual body, adding nothing. Fire correlates the sale with its numbering through
    the `orderCode`.
  </Step>
  <Step title="The authority approves">
    Minutes later. Fire receives the provider's result and updates the order. Query this same
    request if you need to see it.
  </Step>
</Steps>

<Warning>
  **The sale is never blocked by fiscalization.** If the provider does not answer in time,
  this endpoint returns `202` with an explicit state: you print a provisional ticket, inject
  the order anyway, and Fire completes the numbering on its own. What you must not do is
  retry in a loop or hold the sale.
</Warning>

## Headers

<ParamField header="x-api-key" type="string" required>
  Your Fire API key, with the **Fiscal Gateway (numbering)** permission.

  Account and vendor are derived from the key, **never from the body**. That is why the
  payload carries no `accountId` or `vendorId`: a credential cannot lie about who it belongs
  to.
</ParamField>

<ParamField header="Idempotency-Key" type="string" required>
  UUID identifying **this fiscal operation**. If you retry after a network failure, send the
  **same** value: you get the previous result instead of a new document.

  Generate it once per sale and keep it with the order until you inject it. If you reuse it
  with a different body, Fire answers `409`: they are two different operations, and returning
  the first one would hand this sale another sale's document.
</ParamField>

## Body

This is **its own payload**, not the order injection one: only what is needed to number. The
names match the ones you already use (`store`, `device`, `orderCode`) so you can build it by
trimming what you have — but do not send the full order body: no `products`, no `payments`,
no `shippingMethod`.

Seven fields, and none of them is a tax authority code.

<ParamField body="orderCode" type="string" required>
  Code of the sale. It is **the idempotency key**, both Fire's and the provider's.

  It must be unique per account and country, and **the same** you later send when injecting
  the order. If two stores of the same account use the same `orderCode`, Fire stops with
  `409` before issuing: without that guard the second store would print the first one's
  sequential.
</ParamField>

<ParamField body="createdAt" type="string" required>
  Order creation timestamp.

  It is only the **fallback** for the issue date: the primary source is the store's open
  business day. A sale made after midnight belongs to the day that is still open, not to the
  clock's.

  Without a timezone (`2026-08-12 17:26:09`) it is read as **UTC**.
</ParamField>

<ParamField body="operation" type="string" default="INVOICE">
  What you are asking for. One of:

  - `INVOICE` — number the sale.
  - `CANCEL` — void it. Fire finds the original document of that same order on its own: **do
    not send fiscal keys or Fire identifiers**.
</ParamField>

<ParamField body="store" type="object" required>
  The issuing store. From `code`, Fire resolves the country, the issuer's fiscal identity and
  the establishment — do not send them yourself.
  <Expandable title="store">
    <ParamField body="code" type="string" required>Store code in Fire (e.g. `K004`).</ParamField>
  </Expandable>
</ParamField>

<ParamField body="device" type="object" required>
  The issuing device. **It is the only block that differs from order injection**:
  `externalId` is added.
  <Expandable title="device">
    <ParamField body="uid" type="string" required>
      Device identifier.
    </ParamField>
    <ParamField body="externalId" type="string" required>
      **Point of emission** that device issues from. It travels to the provider exactly as
      you declare it.

      Two registers in the same store number independently, so it cannot be inferred or
      shared: each device declares its own. Without this field Fire answers `400` — there is
      nothing sensible to invent in its place.
    </ParamField>
  </Expandable>
</ParamField>

<ParamField body="metadata" type="object">
  **Sale-level** key-value: what changes on every transaction and some country requires.

  It is opaque to your integration: Fire does not interpret it, it transports it. Valid keys
  depend on the store's country, and an unknown key is rejected with `400` — a Fire error is
  better than an invented field travelling to the tax authority.

  Most of the time it is empty: **whatever is constant about the store is not sent here**, it
  is configured once (see below).
</ParamField>

<ParamField body="reason" type="string">
  Reason for the cancellation. Stored for support.
</ParamField>

### What you do not send: the store configuration

Everything **constant about the store** is configured once in the backoffice and travels on
its own: the issuer's fiscal identity, and a **per-country key-value block** for whatever
attributes that country's provider needs.

<Info>
  That key-value lives in the store's fiscal configuration, **separated by country**. It is
  why this endpoint is the same everywhere: what is specific to each country is administered,
  not programmed and not sent on every sale.

  If your integration starts needing a new per-country field, the answer is almost always to
  configure it there — not to add it to the payload.
</Info>

<ParamField body="referencedFiscalRequestId" type="string">
  Only for `CANCEL`, and only when automatic resolution is not enough: a cancellation
  referencing a document from another order, or several invoices for the same one.

  **In the normal case, do not send it.** Fire finds the original through the natural key, so
  your point of sale does not need to store any identifier of ours to be able to void a sale.
</ParamField>

## Response

<ResponseField name="fiscalRequestId" type="string">
  Identifier of the request in Fire. This is what you query the outcome with.
</ResponseField>

<ResponseField name="orderCode" type="string">Echo of the code you sent.</ResponseField>

<ResponseField name="reused" type="boolean">
  `true` if this request already existed and was returned as-is, without numbering again.
</ResponseField>

<ResponseField name="requestStatus" type="string">
  State of **the numbering**: did I get numbers to print?

  `GENERATED` · `PENDING` · `FAILED_RETRYABLE` · `FAILED_FINAL` · `UNAVAILABLE`
</ResponseField>

<ResponseField name="documentStatus" type="string">
  State of the **document before the tax authority**: did it approve?

  `PENDING` · `AUTHORIZED` · `REJECTED` · `CANCELLED`

  <Note>
    In this response it is **always** `PENDING`: there are numbers, there is no verdict. Only
    the provider's result moves it, and that arrives later. Collapsing both states into one
    is the mistake that makes a POS believe a sale is authorized when it is merely numbered.
  </Note>
</ResponseField>

<ResponseField name="document" type="object">
  The receipt's identifiers. `null` if nothing was numbered.
  <Expandable title="document">
    <ResponseField name="documentType" type="string">`SALE_INVOICE` or `CREDIT_NOTE`.</ResponseField>
    <ResponseField name="documentNumber" type="string">
      Visible number, composed per the country's convention (`005-004-000000011`). It is for
      **printing**: to search or reconcile use `sequential` + `serie`.
    </ResponseField>
    <ResponseField name="sequential" type="string">Document sequential.</ResponseField>
    <ResponseField name="serie" type="string">Series. `null` in countries that do not use one.</ResponseField>
    <ResponseField name="authorizationMode" type="string">
      `ONLINE` · `OFFLINE` · `BATCH`. Determines the contingency legend to print.
    </ResponseField>
    <ResponseField name="issuedAt" type="string">Issue date.</ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="countryIdentifiers" type="object">
  What varies per country. It carries `countryCode` inside so it can be read without looking
  outside the block.

  Ecuador and Brazil bring `accessKey`; Venezuela brings `controlNumber` and `accessKey: null`.

  <Warning>
    **`accessKey` can legitimately be `null`.** Do not assume it always comes: it is the
    mistake that breaks multi-country fiscal integrations most often.
  </Warning>
</ResponseField>

<ResponseField name="graphic" type="object">
  Key → **exact string to encode**, ready to render. For example
  `{ "qr": "1208202601…811" }`.

  It is an open map because each country's receipt does not always carry the same thing, and
  a country may need more than one element. **Iterate over the keys you receive**, do not
  look for fixed fields.

  Fire does not generate images: size and resolution depend on your printer, and only whoever
  prints knows that.
</ResponseField>

<ResponseField name="printing" type="object">
  What you may print. **It is a legal rule of the country, not a derivation of whether there
  is a document**: that is why Fire resolves it instead of each channel.
  <Expandable title="printing">
    <ResponseField name="printable" type="boolean">Whether you can hand over the fiscal receipt.</ResponseField>
    <ResponseField name="mode" type="string">
      `FISCAL_DOCUMENT` · `PROVISIONAL_RECEIPT` · `NONE`
    </ResponseField>
    <ResponseField name="reason" type="string">
      `ISSUED_OFFLINE` · `AWAITING_FISCAL_NUMBERING` · `FISCAL_REJECTED` · `null`
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="failure" type="object">
  Why there is no document. `scope` is what you branch on: `TECHNICAL` → print "in progress"
  and move on; `FUNCTIONAL` → some data is wrong and retrying will not fix it.
</ResponseField>

## Status codes

| Code | Meaning |
|---|---|
| `200` with `NOT_APPLICABLE` | This vendor has no fiscal representation. Not an error |
| `201` | Numbered now |
| `200` | Already existed — idempotent retry (`reused: true`) |
| `202` | The provider did not answer within the time budget. Print provisional and inject anyway |
| `200` with `FAILED_FINAL` | Rejected. It is the answer to your question, not a call error |
| `400` | Invalid body, store not configured, or missing point of emission |
| `401` · `403` | Credentials or permission |
| `404` | The store does not exist for your API key's vendor |
| `409` | Same `Idempotency-Key` with a different body, or the `orderCode` was used by another store |

<Note>
  **The call is synchronous, but it has a time budget.** The customer is standing at the
  register: Fire waits a few seconds for the provider and, if there is no answer, it cuts and
  returns `202` instead of leaving the sale hanging.

  That `202` is **not a promise that it will reach your POS later through another channel**:
  it is Fire saying "no numbers yet, print provisional and move on". The numbering is
  completed on Fire's side and you query it whenever you want with the `fiscalRequestId`. It
  is rare, but it exists because the alternative — failing the sale — is worse.
</Note>

## What to do with each response

<AccordionGroup>
  <Accordion title="GENERATED — the normal case">
    Print the receipt with `document.documentNumber` and render the codes in `graphic`.
    Inject the order.

    If `printing.reason` is `ISSUED_OFFLINE`, the receipt is valid but was issued in
    contingency: print the legend that country requires.
  </Accordion>

  <Accordion title="PENDING or FAILED_RETRYABLE — the provider did not answer">
    `printing.mode` comes as `PROVISIONAL_RECEIPT`. Print a non-fiscal ticket and inject the
    order anyway.

    **Do not retry this call.** Fire completes the numbering on its own. If you need to show
    the result, query with the `fiscalRequestId`.
  </Accordion>

  <Accordion title="FAILED_FINAL — the authority or the provider rejected it">
    Some data is not accepted and retrying will not fix it: read `failure.message`, which
    carries the real reason (for example, that the store is not registered in the fiscal
    catalog).

    Print the provisional ticket, inject the order, and escalate with the `fiscalRequestId`.
  </Accordion>

  <Accordion title="4xx — the problem is in the request">
    In these cases **no fiscal request was created**: fix it and call again.

    If you get a `404` about a store not found, check that your API key belongs to the vendor
    that owns that store — the message includes which vendor it searched against.
  </Accordion>
</AccordionGroup>

<Info>
  **Always call it. This is how you find out whether the store numbers.**

  You do not need to sync configuration or branch by country: if that vendor has no fiscal
  representation, the answer is `200` with `requestStatus: "NOT_APPLICABLE"` and
  `printing.mode: "NONE"` — you print your ticket and move on. **It is not an error** and no
  request is created.

  It is the same branch you already have: you branch on `printing.mode`, not on the HTTP status
  code.
</Info>

## Querying a request

These are two read endpoints, and they exist for **when the normal path is not enough**: you
lost the synchronous response, or you want to see whether the authority already approved
without waiting for the event. In day-to-day operation you should not need them — the data
arrives through the order events.

By identifier:

```
GET /api/v1/external/fiscal/numbering/{fiscalRequestId}
```

By order — returns `items[]`, because an order can have **two** documents: the invoice and
the cancellation compensating it.

```
GET /api/v1/external/fiscal/numbering?orderCode=FUEL-EC-1786579046934
```

This is what you use when you lose the response to a network failure: the `orderCode` is the
only thing you have at hand.

When the authority approves, `documentStatus` becomes `AUTHORIZED`.
