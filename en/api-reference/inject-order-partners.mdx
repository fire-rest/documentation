Injects into Fire an order coming from **X-MART Gateway**. It is the adapter dedicated to that
integrator: the body is the same, in Fire format, as the one in
[Create order (v1)](/en/api-reference/create-order), and the order goes through the same core:
same validations, same business day, same taxes, same fiscal document, and same
[events](/en/events/overview).

What changes compared to `create-order`:

- **The store comes from the body.** Fire looks it up by `store.code` + `store.vendorId`. The path
  carries no store code, even though it hangs from `/stores/`.
- **The account is resolved from the store**, not from the API key nor from the body's
  `accountId`.
- **The legacy numeric channel is translated.** If the order has no `channel.code` but does have
  `channelId` (the numeric id X-MART uses to combine channel and service), Fire translates it into
  channel + service. If it doesn't recognize it, the order is created anyway.
- **The `201` response carries `_adapter: "xmart"`.**

## Authentication

<ParamField header="x-api-key" type="string" required>
  Your Fire API key (`pk_live_...`) with the `orders:write` scope. `Authorization: Bearer pk_live_...`
  is also accepted; if both arrive, `x-api-key` wins. The key **must be bound to an account and to
  a vendor**: a key without an account is rejected with `403`.
</ParamField>

<ParamField header="Content-Type" type="string" required>
  `application/json`.
</ParamField>

## Body

The body is the order JSON, **unwrapped** (not `{ "payload": { ... } }`). Amounts go as decimal
numbers (`22.9`). Fields not listed on this page do not cause an error.

### Channel and service

The main source is `channel.code` for the channel and `service.code` for the service. If
`channel.code` is missing and `channelId` arrives, Fire translates that numeric id into channel +
service according to Fire's channel configuration. If there is no `channel.code` and no recognized
`channelId`, the channel comes from `channelName`; and if there is no `service.code`, the service
comes from the translation or from `selectedShippingMethod`.

Channel resolution **never rejects the order**: a `channelId` Fire doesn't recognize is not an
error.

**A PIX** goes as `method: "DIGITAL"` + `processor: "PIX"`:

```json
{ "method": "DIGITAL", "processor": "PIX", "currencyCode": "BRL", "transactionStatus": "APPROVED", "totalBill": 22.9, "changeAmount": 0 }
```

**Aggregator discount.** An entry with `paymentMethodCode: "AGGREGATOR_DISCOUNT"` is not a real
payment: it is a discount funded by the aggregator (for example iFood). It goes in
`paymentMethods[]` next to the real payments and its `totalBill` counts in the sum of payments; it
is left out of the cash close and of the fiscal document.

**Cash.** In a `CASH` payment with `customerCashAmount`, the cash handed over must cover the bill
and `changeAmount` must be the difference.

not go here; it goes in `payments.shippingCost[]`.

### Fiscal data

The buyer data for the fiscal document comes from `client.billingInformation` and, if it isn't
there, from `client`:

| `billingInformation` key | Use |
|---|---|
| `govIdType` | Document type. Takes priority over `client.govIdType` |
| `govIdNumber` | Document number. Takes priority over `client.govIdNumber` |
| `name`, then `businessName` | Name. If missing, `client.name` + `client.lastName` |
| `email` | Email. If missing, `client.email` |
| `address` | Address |

The phone comes only from `client.phone`.

**Final consumer.** If the type is `FINAL_CONSUMER` or the document is not valid —in Brazil, a CPF
or CNPJ of 11 or 14 digits; in other countries, between 6 and 13 alphanumeric characters—, Fire
treats the buyer as a final consumer and discards what came from the channel (`CONSUMIDOR`,
`00000000000`, generic emails). If the account has final-consumer data configured, Fire uses that.

## Order status

The payments' `transactionStatus` (case-insensitive) decides the status the order is born with and
which event goes out:

| Payments' `transactionStatus` | `status` | `payment_status` | Event |
|---|---|---|---|
| All `APPROVED` | `COMPLETED` | `SUCCEEDED` | [`order.completed`](/en/events/order-completed) |
| Any `REJECTED`, `FAILED`, or `CANCELLED` | `OPEN` | `FAILED` | [`order.opened`](/en/events/order-opened) |
| Other (`PENDING`, `AUTHORIZED`…) | `OPEN` | `PENDING` | [`order.opened`](/en/events/order-opened) |

Only `APPROVED` approves: an `AUTHORIZED` payment leaves the order open. Every new order fires
exactly one of the two events. If the event can't be queued, the order is created anyway.

## Duplicates

The duplicate key is **`orderId` + `store.vendorId`**. If you resend an order that already came in,
the response is `409` with `code: "DUPLICATE_ORDER"` and `data` carries the existing order's `id`,
`externalOrderId`, and `status`. **Treat it as "already ingested", not as a failure:** the order is
not rewritten and no events are emitted again.

The same `orderId` with a different `store.vendorId` is a different order. There is no
`Idempotency-Key` header.

<Note>
  The order validation rules run before the duplicate check. If an order came in while a rule did
  not yet reject and you resend it after the rule is enabled, you get that rule's `400` instead of
  the `409`.
</Note>

## Errors

Every error carries `success: false`, `error` (the category), and `message`; some carry `code`,
`data`, or `details`. This endpoint **does not return `422`**: business rejections are `400`
`BUSINESS_ERROR`.

| HTTP | `error` / `code` | When |
|---|---|---|
| `400` | `VALIDATION_ERROR` | `orderCode` is missing or empty; also with an empty body or invalid JSON. `message`: `orderCode is required and must be a non-empty string` |
| `400` | `VALIDATION_ERROR` | The body doesn't have the right shape. `details` lists each problem with its `path` |
| `401` | `UNAUTHORIZED` | The API key is missing, doesn't start with `pk_live_`, or is expired or revoked |
| `403` | `FORBIDDEN` | API key without the `orders:write` scope, or not bound to an account |
| `404` | `NOT_FOUND` | There's no store with that `store.code` + `store.vendorId`. `message`: `Store not found with ID <code>` |
| `400` | `BUSINESS_ERROR` | Store inactive or not published. `message`: `Store <code> is not active or not published. …` |
| `400` | `BUSINESS_ERROR` | Business day closed. `message`: `Store <code> business day is not open. …` |
| `400` | `BUSINESS_ERROR` + `details.code: ORDER_INVARIANT_VIOLATION` | The order breaks a validation rule enabled for your vendor. See below |
| `409` | `CONFLICT` / `DUPLICATE_ORDER` | The order already existed for that vendor. See [Duplicates](#duplicates) |
| `400` | `DOMAIN_ERROR` or `BUSINESS_ERROR` with a `message` starting with `Failed to` | An internal Fire failure, not a problem with your order |
| `503` | `SERVICE_UNAVAILABLE` | The API key couldn't be verified at that moment |
| `500` | `INTERNAL_SERVER_ERROR` | Unexpected error |

### Rejection by validation rules

Each vendor can enable, per channel, rules that check the order before saving it. An order that
passes the shape validation can still be rejected here. The rejection adds no keys at the root:
everything new goes in `details`.

| `details.violations[].category` | What happened |
|---|---|
| `TAX_MISSING` | A product or modifier with a price carries no taxes |
| `TAX_MALFORMED` | Incomplete taxes (missing `name`, `rate`, `amount`, or `base`), taxes that don't add up to the tax total, or the same tax written two ways |
| `ORDER_NOT_BALANCED` | The products don't add up to the order total |
| `PRODUCT_NOT_MAPPED` | A product without `additionalInfo.externalCode` |
| `CASH_CHANGE_INVALID` | A cash payment with inconsistent change |
| `PRODUCT_TYPE_MISMATCH` | A product or modifier sent with a `type` different from the synchronized menu, or without `type`. `expected` is the menu type; `received`, the one you sent (empty if you sent none) |

Each violation carries `invariant`, `category` (stable, for automation), `path` (the path within the
body you sent, such as `order.products[0]`), `expected` and `received` in decimals, and `message`.
In `ORDER_NOT_BALANCED`, `lines` says how much each product adds up to.

<Note>
  Passing the shape validation doesn't guarantee the order is accepted. The example on this page
  carries no `taxes[]` per product: with the tax rule enabled for your vendor, it would be rejected
  with `TAX_MISSING`.
</Note>

```json
{
  "success": false,
  "error": "BUSINESS_ERROR",
  "message": "Order rejected — 1 problem. [I6] order.products: the products add up to 73.70 but the order total is 75.70 (difference 2.00). A product, an option or a price is missing.",
  "details": {
    "code": "ORDER_INVARIANT_VIOLATION",
    "orderCode": "AGG-KEETA-K066-…",
    "externalOrderId": "…",
    "violations": [
      { "invariant": "I6", "category": "ORDER_NOT_BALANCED", "path": "order.products", "expected": "75.70", "received": "73.70",
        "message": "…", "lines": [{ "path": "order.products[0]", "externalCode": "30033", "name": "…", "total": "73.70" }] }
    ]
  }
}
```

### When to retry

| Response | What to do |
|---|---|
| `201` | Nothing. |
| `409` `DUPLICATE_ORDER` | **Don't retry**: the order is already there. Use `data.id`. |
| `400` `VALIDATION_ERROR`, `400` with `ORDER_INVARIANT_VIOLATION`, `401`, `403`, `404` | Fix and resend with the same `orderId`. An identical retry fails the same way. |
| `400` `BUSINESS_ERROR` for an inactive store or a closed day | Retry when the state changes. After the day opens, the store can take up to 30 seconds to accept orders. |
| `400` with a `message` starting with `Failed to`, `503`, `500` | Retry with backoff. It's safe: if the order had already come in, the response is `409`. |
