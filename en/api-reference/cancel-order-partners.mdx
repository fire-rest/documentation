Cancels an order you injected, looking it up by **the external id you gave it**. Unlike the
backoffice endpoint, you do not need to store our internal UUID.

<Info>
  This endpoint runs the **cancellation policy**: Fire's rules plus whatever the account
  configured. Before trying, you can ask [Cancellation
  eligibility](/en/api-reference/cancellation-eligibility), which returns the same verdict and
  the same `code` with a `200` and no side effects.
</Info>

## The order of the steps depends on the fiscal gateway

This is the part integrations get wrong most often, and the only place where the order
matters.

<Tabs>
  <Tab title="With gateway numbering">
    Fire numbers the receipt, so **the fiscal void comes first**:

    <Steps>
      <Step title="Void the receipt">
        `POST /api/v2/external/fiscal/numbering` with `operation: "CANCEL"`. It returns the
        credit note. See [Fiscal numbering v2](/en/api-reference/fiscal-documents-v2).
      </Step>
      <Step title="Cancel the order">
        Only now, this endpoint.
      </Step>
    </Steps>

    It is the same pattern as issuing — the fiscal fact first, the order second — which makes
    it easy to remember: **you void the way you issue**.

    If you invert the steps, this endpoint answers `409` with
    `FISCAL_REPRESENTATION_NOT_VOIDED`. It is not transient: retrying will not fix it.

    <Note>
      `/fiscal/numbering` is deprecated: it keeps working until the end of December 2026, and void at
      cancellation (the third tab) replaces it. See [Fiscal numbering v2](/en/api-reference/fiscal-documents-v2).
    </Note>
  </Tab>
  <Tab title="Without gateway numbering">
    There is no prior void to request: **cancel directly**, with this endpoint and nothing
    else.
  </Tab>
  <Tab title="With void at cancellation">
    When the vendor has **void at cancellation** (`voidAtCancellation`, off by default), there is no
    prior step: **you only call this endpoint**. Fire asks the provider for the credit note inside this
    same request, after the cancellation policy approves and before cancelling.

    - If the credit note comes out, the order is cancelled and the `200` carries it in
      [`fiscal.fiscalRepresentation`](#the-fiscal-block-in-the-response), ready to print.
    - If the credit note does not come out, `409` and **the order is not cancelled**. `code` and
      `data.retryable` tell you what to do: see the
      [void-at-cancellation rules](#fiscal-gateway-void-at-cancellation).
    - If your register voided beforehand with `/fiscal/numbering` and the policy approves, the cancel
      answers `200` with **that same** credit note in `fiscal.fiscalRepresentation`: Fire does not
      issue another. The policy still runs: if the day closed or an account rule denies, there is a
      `409` even though the note exists.
    - If the issuer already voided the document (the order's fiscal status moved to `cancelled`
      through its callback) and the order is still alive, the cancel answers `200` and the order is
      cancelled: Fire does not request another credit note. The policy still runs.

    In this mode `FISCAL_REPRESENTATION_NOT_VOIDED` does not come back: the register no longer has to
    request the credit note.

    The call can take up to about 5 s longer (the wait for the provider): give your HTTP client a
    generous timeout. The document can be read again afterwards with
    [Fiscal print v2](/en/api-reference/fiscal-print).
  </Tab>
</Tabs>

Fire works out which of the three cases applies on its own, from that account, country and
vendor's configuration. **You do not have to find out**: if you have to request the credit note
first, the `409` tells you (`FISCAL_REPRESENTATION_NOT_VOIDED`).

## What a rejection carries

Beyond the `code`, a `409` body carries the reason ready to display:

<ResponseField name="message" type="string">
  The headline: the name of the rule that denied. This is what fits in a short notice.
</ResponseField>

<ResponseField name="data.reasonDetail" type="string">
  The long why. Only present when the rule has one: which Fire rules carry it is listed in
  [Fixed Fire rules](#fixed-fire-rules). It travels apart from `message` so you can show just the
  headline when there is no room for more.
</ResponseField>

<ResponseField name="data.threshold / data.actual / data.field">
  The number behind the rejection, when the rule compares one: the limit and the actual value.
  Lets you say "17 minutes past" without parsing the text.
</ResponseField>

<ResponseField name="data.resolvedFrom" type="object">
  What it decided with. A receipt for diagnosing, not for showing to a person.
</ResponseField>

## Rejection codes

All of them come back as `409`. **Branch on `code`**, never on the message: the text is for a
person to read and may change or be translated without notice.

| `code` | What happened | What to do |
|---|---|---|
| `CANCELLATION_IN_PROGRESS` | A cancellation is already in flight. | Do not retry: check the order again. |
| `ORDER_NOT_CANCELLABLE` | The order is already closed or cancelled. | Nothing: it is a terminal state. |
| `FISCAL_REPRESENTATION_NOT_VOIDED` | Only for vendors **without** void at cancellation: there is an invoice and no credit note yet. | Request the fiscal void first, wait for the response, and only then cancel. |
| `BUSINESS_DAY_CLOSED` | The order belongs to a closed business day, or to one before the active day. | Not cancellable over the API: an accounting adjustment applies. |
| `CANCELLATION_POLICY_DENIED` | A rule configured by the account denied it. | Read `message`: the customer wrote it. |
| `FISCAL_VOID_FAILED` | Only with void at cancellation: the credit note did not come out, so the order was **not** cancelled. It groups four cases (below). | Decide by `code` + `data.retryable`: with `true`, retry the same request; with `false`, fix the configuration or escalate, depending on the rule. |
| `FISCAL_INVOICE_UNRESOLVED` | Only with void at cancellation: the sale's invoice still has no confirmed number (the provider did not answer when it was numbered). Fire asked for it again with the same key and still got no answer, so there was nothing to void and the order was **not** cancelled. | If `data.retryable`, retry the same request: if the provider answers, Fire numbers the invoice, voids it and cancels. If not, escalate. |

`FISCAL_VOID_FAILED` groups four rules: the credit note was rejected, the void could not be
requested, the void is already in progress, and the document could not be voided (each one in
[Fiscal Gateway (void at cancellation)](#fiscal-gateway-void-at-cancellation)). Each part of the
`409` serves one purpose:

- **To decide**: `code` + `data.retryable`. With `true`, retrying the same request can work; with
  `false`, retrying without changing anything gives the same rejection.
- **To show the cashier**: `message` (the rule's name) and `data.reasonDetail` (what happened and
  what to do), in the language of `?locale=`.
- **For your logs**: `data.fiscal.failure` (`code` and `message`), the provider's detail. You do not
  need to branch on it.

<Warning>
  A `200` means **the order** was cancelled. Whether the fiscal document is already voided depends
  on the case: with gateway numbering you voided it in the previous step; with void at cancellation
  Fire voided it in this same request, and the credit note comes in `fiscal`; with native issuing it
  settles later, through the provider's callback.
</Warning>

## The `fiscal` block in the response

<ResponseField name="data.fiscal" type="object | null">
  Only with void at cancellation, when this request voided the receipt: `action: "CONTINUE"`,
  `requestStatus: "GENERATED"`, `retryable`, `failure: null` and **`fiscalRepresentation`**: the
  credit note, with the invoice it voids in `history` and `compensates`. That is what the register
  prints (number, QR) without another request. It also comes when the credit note **already
  existed** (an earlier cancel voided and then failed, or the register voided before) and the policy
  approves: Fire does not void again, but returns it. `null` when the vendor does not void at
  cancellation, the order was never numbered, or the issuer had already voided the document on its
  own (there is no Fire credit note to print).
</ResponseField>

## Fixed Fire rules

These are the cancellation-policy rules Fire ships. They run **always** and before the account's
rules, the account cannot edit or turn them off, and they show on the policy screen in these two
groups. The first one that matches wins.

All of them answer the `409` with the same shape: `code`, `message` (the rule's name, in the
language of `?locale=`; Spanish by default) and, in `data`, the `reasonDetail` —when the rule has
one— and the `resolvedFrom`, the receipt of what was decided with. The names and explanations below
are the English texts (`?locale=en`); with `?locale=es` or `?locale=pt` they come translated.

If two cancellations of the same order arrive at once and both pass the policy, the second one
collides in the database and answers the rule "A cancellation is already in progress"
(`CANCELLATION_IN_PROGRESS`) with the same shape; its `resolvedFrom` is what that request saw when it
passed the policy. Do not retry it: check the order again.

### General

They apply to every account. All five can be anticipated by
[eligibility](/en/api-reference/cancellation-eligibility): the preflight returns the same `code` with
`canCancel: false`. They carry no `data.retryable`: retrying changes nothing while the state that
triggers them remains.

| Rule (`message`) | `code` | When it triggers | `data.reasonDetail` | What to do |
|---|---|---|---|---|
| A cancellation is already in progress | `CANCELLATION_IN_PROGRESS` | The order's fiscal status is `cancelling`: another cancellation is already running. | This order already has a cancellation in progress. Do not retry it: check the order again to see how it ended up. | Do not retry: check the order again. |
| The order is no longer in a cancellable state | `ORDER_NOT_CANCELLABLE` | The order is `FORCE_CLOSED` or `CANCELLED`. | — | Nothing: it is a terminal state. |
| The credit note has not been issued yet | `FISCAL_REPRESENTATION_NOT_VOIDED` | Only for vendors **without** void at cancellation: there is an invoice and no credit note yet. | Request the fiscal void first, wait for the response, then cancel the order. | Void with `/fiscal/numbering` (`operation: "CANCEL"`) and only then cancel. `/fiscal/numbering` is deprecated at the end of December 2026 and void at cancellation replaces it: see [Fiscal numbering v2](/en/api-reference/fiscal-documents-v2). |
| The business day is closed | `BUSINESS_DAY_CLOSED` | The order belongs to a closed business day, or to one before the active day. | The order belongs to a closed day. Re-open the day, or issue a credit memo or adjustment. | Not cancellable over the API while the day stays closed. |

### Fiscal Gateway (void at cancellation)

Only for vendors with [void at cancellation](#the-order-of-the-steps-depends-on-the-fiscal-gateway),
except for one case of "The tax document could not be voided" (below).
Fire evaluates them **after** asking the provider for the credit note, with what the provider
answered; that is why eligibility cannot anticipate them: in the preflight the order comes out
cancellable and the "no" is only known when cancelling. The one exception is **The credit note was
rejected**: if the authority already rejected a credit note for this sale, eligibility already
answers `canCancel: false` with `FISCAL_VOID_FAILED`, and the cancel denies it without calling the
provider again.

On top of what any rule carries, their `409` brings:

- `data.retryable`: whether retrying the same request can work.
- `data.fiscal`: `{ action: "REJECT", requestStatus, retryable, failure: { code, message } }`, the
  provider's detail. `failure.message` comes in the language of `?locale=` when Fire knows the
  `failure.code` (timeout, no connection, no device…); the text of an authority rejection comes as
  it arrived.

| Rule (`message`) | `code` | Can eligibility anticipate it? | `data.retryable` |
|---|---|---|---|
| The invoice does not have a confirmed number yet | `FISCAL_INVOICE_UNRESOLVED` | No | The provider's (`true` if it did not answer) |
| The credit note was rejected | `FISCAL_VOID_FAILED` | **Yes** | `false` |
| The fiscal void could not be requested | `FISCAL_VOID_FAILED` | No | `false` in general |
| The void of this sale is already in progress | `FISCAL_VOID_FAILED` | No | `true` |
| The tax document could not be voided | `FISCAL_VOID_FAILED` | No | `true` |

The examples use `?locale=en` and a shortened `resolvedFrom`.

#### The invoice does not have a confirmed number yet

- **`code`**: `FISCAL_INVOICE_UNRESOLVED`.
- **When it triggers**: the sale's invoice was left without a confirmed number (the provider did not
  answer when it was numbered). Fire asked for it again with the same key and it still had no
  number, so there was nothing to void.
- On that retry of the invoice, "The void of this sale is already in progress" and "The fiscal void
  could not be requested" can also come out, depending on the `failure.code`.
- **Eligibility**: does not anticipate it.
- **Retry**: yes, when `data.retryable` is `true`. If the provider answers, Fire numbers the
  invoice, voids it and cancels in the same request.
- **What to do**: retry the cancellation; if it stays the same, escalate.

```json 409 — The invoice does not have a confirmed number yet
{
  "success": false,
  "error": "CONFLICT",
  "code": "FISCAL_INVOICE_UNRESOLVED",
  "message": "The invoice does not have a confirmed number yet",
  "data": {
    "reasonDetail": "The fiscal provider did not confirm the invoice number, so there is nothing to void. The order was not cancelled: retry the cancellation and, if it stays the same, escalate.",
    "resolvedFrom": {
      "orderStatus": "COMPLETED",
      "paymentStatus": "SUCCEEDED",
      "countryCode": "EC",
      "fiscalStatus": "processing",
      "fiscalVoidResult": "INVOICE_UNRESOLVED"
    },
    "retryable": true,
    "fiscal": {
      "action": "REJECT",
      "requestStatus": "PENDING",
      "retryable": true,
      "failure": {
        "code": "PROVIDER_TIMEOUT",
        "message": "The fiscal provider did not answer in time. Retry the cancellation."
      }
    }
  }
}
```

#### The credit note was rejected

- **`code`**: `FISCAL_VOID_FAILED`.
- **When it triggers**: the fiscal provider or the authority rejected the credit note for good (not
  because of configuration). Also when a credit note for this sale had **already** been rejected:
  Fire does not call the provider again.
- **Eligibility**: **yes**, it anticipates it when the note was already rejected before.
- **Retry**: no (`data.retryable: false`): retrying would give the same rejection.
- **What to do**: escalate to review the sale.

`data.fiscal.failure` carries the authority's rejection: `FISCAL_BUSINESS_RULE` or the provider's
own code, with its text as it arrived. If Fire does not have it
stored (a note rejected earlier), it comes as `CREDIT_NOTE_REJECTED`: "The credit note of this sale
was rejected.".

```json 409 — The credit note was rejected
{
  "success": false,
  "error": "CONFLICT",
  "code": "FISCAL_VOID_FAILED",
  "message": "The credit note was rejected",
  "data": {
    "reasonDetail": "The fiscal provider or the tax authority rejected the credit note, and retrying would give the same rejection: the order cannot be cancelled. Escalate to review the sale.",
    "resolvedFrom": {
      "orderStatus": "COMPLETED",
      "paymentStatus": "SUCCEEDED",
      "countryCode": "EC",
      "fiscalStatus": "processing",
      "fiscalVoidResult": "FAILED_FINAL"
    },
    "retryable": false,
    "fiscal": {
      "action": "REJECT",
      "requestStatus": "FAILED_FINAL",
      "retryable": false,
      "failure": {
        "code": "FISCAL_BUSINESS_RULE",
        "message": "Rejected by the tax authority: …"
      }
    }
  }
}
```

#### The fiscal void could not be requested

- **`code`**: `FISCAL_VOID_FAILED`.
- **When it triggers**: the fiscal configuration of the vendor or of the register is missing or
  failing; it is not an authority rejection. `failure.code` is `PROVIDER_AUTH_FAILED`,
  `FISCAL_COUNTRY_NOT_SUPPORTED`, `FISCAL_CONFIGURATION_ERROR`, `FISCAL_DEVICE_MISSING` or
  `FISCAL_IDEMPOTENCY_CONFLICT`.
- **Eligibility**: does not anticipate it.
- **Retry**: not without fixing first (`data.retryable` is `false` in general).
- **What to do**: fix the configuration (provider credentials, country, register device) and retry.
  With `FISCAL_IDEMPOTENCY_CONFLICT` (this sale's key already voided another `orderCode`) no retry
  fixes it: escalate.

```json 409 — The fiscal void could not be requested
{
  "success": false,
  "error": "CONFLICT",
  "code": "FISCAL_VOID_FAILED",
  "message": "The fiscal void could not be requested",
  "data": {
    "reasonDetail": "The vendor's fiscal configuration is missing or failing (provider credentials, country, register device). The order was not cancelled: fix the configuration and retry.",
    "resolvedFrom": {
      "orderStatus": "COMPLETED",
      "paymentStatus": "SUCCEEDED",
      "countryCode": "EC",
      "fiscalStatus": "processing",
      "fiscalVoidResult": "NOT_VOIDABLE"
    },
    "retryable": false,
    "fiscal": {
      "action": "REJECT",
      "requestStatus": "FAILED_FINAL",
      "retryable": false,
      "failure": {
        "code": "PROVIDER_AUTH_FAILED",
        "message": "The API key does not belong to this provider."
      }
    }
  }
}
```

#### The void of this sale is already in progress

- **`code`**: `FISCAL_VOID_FAILED`.
- **When it triggers**: another request is voiding this same sale right now (`failure.code` is
  `VOID_IN_PROGRESS`).
- **Eligibility**: does not anticipate it.
- **Retry**: yes (`data.retryable: true`), after a few seconds.
- **What to do**: wait a few seconds and retry the cancellation.

```json 409 — The void of this sale is already in progress
{
  "success": false,
  "error": "CONFLICT",
  "code": "FISCAL_VOID_FAILED",
  "message": "The void of this sale is already in progress",
  "data": {
    "reasonDetail": "Another request is voiding this sale right now. Wait a few seconds and retry the cancellation.",
    "resolvedFrom": {
      "orderStatus": "COMPLETED",
      "paymentStatus": "SUCCEEDED",
      "countryCode": "EC",
      "fiscalStatus": "processing",
      "fiscalVoidResult": "IN_PROGRESS"
    },
    "retryable": true,
    "fiscal": {
      "action": "REJECT",
      "requestStatus": "FAILED_RETRYABLE",
      "retryable": true,
      "failure": {
        "code": "VOID_IN_PROGRESS",
        "message": "The void of this sale is already in progress. Wait a few seconds and retry."
      }
    }
  }
}
```

#### The tax document could not be voided

- **`code`**: `FISCAL_VOID_FAILED`.
- **When it triggers**: the provider did not issue the credit note but it can be retried (timeout,
  no connection, provider unavailable…), or Fire could not verify the fiscal document
  (`failure.code` is `FISCAL_STATE_UNAVAILABLE`): cancelling without seeing it could leave the
  invoice alive with the money refunded. This case is **not only with void at cancellation**: it also
  comes out when Fire could not read the vendor's configuration and the order was numbered by the
  gateway.
- **Eligibility**: does not anticipate it.
- **Retry**: yes (`data.retryable: true`).
- **What to do**: retry the cancellation.

```json 409 — The tax document could not be voided
{
  "success": false,

    "resolvedFrom": {
      "orderStatus": "COMPLETED",
      "paymentStatus": "SUCCEEDED",
      "countryCode": "EC",
      "fiscalStatus": "processing",
      "fiscalVoidResult": "FAILED_RETRYABLE"
    },
    "retryable": true,
    "fiscal": {
      "action": "REJECT",
      "requestStatus": "PENDING",
      "retryable": true,
      "failure": {
        "code": "PROVIDER_TIMEOUT",
        "message": "The fiscal provider did not answer in time. Retry the cancellation."

    }
```
